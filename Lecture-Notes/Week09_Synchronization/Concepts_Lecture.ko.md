## 1. 배경과 임계 구역 문제

### 1.1 협력 프로세스와 데이터 불일치

**협력 프로세스(cooperating process)** 란 다른 프로세스의 실행에 영향을 주거나 영향을 받을 수 있는 프로세스이다. 협력에는 **공유 상태**가 필요하며, 공유 상태는 다음과 같은 방식으로 교환된다.

- **공유 메모리**: 여러 프로세스가 같은 메모리 영역을 매핑한다.
- **메시지 전달**: 프로세스들이 명시적으로 메시지를 주고받는다.
- **논리 주소 공간 공유**: 한 프로세스 안의 여러 스레드가 모두 같은 주소 공간을 공유한다.

근본 문제는 **공유 데이터에 대한 동시 접근이 비일관적인 결과를 만들 수 있다**는 점이다. 접근 순서를 정하는 규율이 없으면 공유 데이터의 최종 상태는 명령어가 어떻게 인터리빙되는가에 따라 달라진다.

> **참고:** **동기화 도구 전체의 토대가 되는 이유.** 락, 세마포어, 모니터 등 앞으로 다룰 모든 동기화 도구는 단 하나의 이유로 존재한다. 공유 데이터에 대한 동시 접근에 **질서 있는 실행**을 부여하여 정확성이 더 이상 운에 좌우되지 않게 만드는 것이다.

### 1.2 경쟁 조건

**경쟁 조건(race condition)** 이란 둘 이상의 프로세스(또는 스레드)가 공유 데이터에 동시에 접근할 때 **접근이 인터리빙되는 순서에 따라 최종 결과가 달라지는** 현상이다.

**고전적인 예시.** 생산자 스레드는 `count++`를, 소비자 스레드는 `count--`를 실행하며 초깃값은 `count = 5`이다. `++`와 `--`는 모두 **load → modify → store**로 분해되므로, 운 나쁜 인터리빙에서는 둘 중 하나의 갱신이 사라진다.

```text
T0: producer  register1 = count        {register1 = 5}
T1: producer  register1 = register1+1  {register1 = 6}
T2: consumer  register2 = count        {register2 = 5}
T3: consumer  register2 = register2-1  {register2 = 4}
T4: producer  count = register1        {count = 6}
T5: consumer  count = register2        {count = 4}  ← 잘못된 값!
```

*그림 1. 생산자와 소비자의 인터리빙으로 갱신 하나를 잃는 실행 순서*

올바른 최종 값은 `count = 5`이다(증가 1회와 감소 1회). 인터리빙에 따라 결과는 **4**(소비자가 마지막으로 씀) 또는 **6**(생산자가 마지막으로 씀)이 될 수 있다. 값이 1만큼 어긋나는 이 **갱신 손실(lost update)** 은 타이밍에 의존하므로 재현하기 매우 어렵다.

**해결책:** 공유 데이터를 건드리는 코드 영역인 **임계 구역(critical section)** 을 식별하고 보호하여 한 번에 한 스레드만 들어갈 수 있게 한다.

> **참고:** **경쟁 조건이 실무에서 두려운 이유.** 경쟁 조건은 타이밍에 의존하므로 개발 중에는 모든 테스트를 통과하고 운영 환경의 부하 상황에서만 드러나는 경우가 많다. 1985~87년 Therac-25(방사선 치료기)에서 환자를 사망에 이르게 한 결함도 운영자 입력 처리의 경쟁 조건이었다. 동기화는 단순한 스타일의 문제가 아니라 **정확성**의 문제이다.

### 1.3 커널에서의 경쟁 조건

커널은 모든 프로세스를 위해 광범위한 공유 상태를 다루므로 커널의 경쟁 조건은 시스템 전체를 망가뜨릴 수 있다.

- **`fork()`** 는 `next_available_pid` 카운터를 유지한다. 두 `fork()` 호출이 어느 쪽도 갱신하기 전에 같은 값을 읽으면 **두 프로세스가 같은 PID를 갖게** 된다.
- 여러 프로세스가 동시에 파일을 열면 **열린 파일 테이블**의 수정이 서로 충돌할 수 있다.
- **메모리 할당자**의 자료 구조(free list, zone count)가 깨질 수 있다.
- `fork()`와 `exit()`에서의 **프로세스 리스트** 갱신과 공유 자료 구조를 건드리는 **인터럽트 핸들러**도 같은 위험에 노출된다.

커널 개발자는 이러한 경쟁 조건을 **체계적으로 방지** 해야 하며, 사용자 공간 프로그래머는 그 규율의 혜택을 받는다.

### 1.4 임계 구역 문제

각 프로세스는 임계 구역을 중심으로 다음과 같이 구성된다.

```c
while (true) {
    /* entry section */
        /* critical section */
    /* exit section */
        /* remainder section */
}
```

임계 구역 문제의 올바른 해법은 다음 **세 가지 요건**을 모두 만족해야 한다.

1. **상호 배제(Mutual Exclusion)**: 어느 시점에도 임계 구역 안에는 한 프로세스만 있어야 한다.
2. **진행(Progress)**: 임계 구역에 아무도 없고 들어가려는 프로세스가 있다면, 어느 프로세스가 들어갈지 결정하는 일을 무한정 미룰 수 없다. (잔여 구역에 있는 프로세스는 누구의 진입도 막을 수 없다.)
3. **한정 대기(Bounded Waiting)**: 어떤 프로세스가 진입을 요청한 뒤 그 요청이 받아들여지기 전까지 다른 프로세스가 임계 구역에 진입할 수 있는 횟수에 **상한**이 있어야 한다.

> **참고:** **각 요건이 막아 주는 것.**
> - **상호 배제**가 없으면 경쟁 조건이 다시 나타난다.
> - **진행**이 없으면 임계 구역이 비어 있는데도 시스템이 멈추는 설계상의 데드락이 가능하다.
> - **한정 대기**가 없으면 다른 프로세스들이 계속 들어가는 동안 특정 프로세스만 영영 들어가지 못하는 기아(starvation)가 생길 수 있다.

### 1.5 선점형 vs 비선점형 커널

커널은 자신의 스레드가 커널 모드에서 실행 중일 때 선점될 수 있는지를 정해야 한다.

- **비선점형 커널**: 커널 모드 코드는 블록되거나, 종료하거나, 양보할 때까지 계속 실행된다. 단일 CPU에서는 다른 커널 스레드가 끼어들 수 없으므로 커널 데이터에 대한 경쟁 조건이 **본질적으로 회피**된다. 단점은 **응답성이 떨어진다**는 것이다(높은 우선순위의 사용자 작업이 커널이 끝날 때까지 기다려야 할 수 있다).
- **선점형 커널**: 커널 모드 코드 자체도 선점될 수 있다. 응답성이 좋고 실시간 작업에 적합하지만, 특히 **SMP** 환경에서는 경쟁 조건을 막도록 신중하게 설계해야 한다.

실무적으로 중요한 점은 두 가지이다.
- **단일 프로세서** 시스템은 임계 구역 동안 **인터럽트를 비활성화**하는 것만으로 상호 배제를 저렴하게 구현할 수 있다.
- **다중 프로세서** 시스템에서는 모든 코어의 인터럽트를 끄는 비용이 크므로 메모리 배리어, 원자 명령, 락 같은 다른 메커니즘이 필요하다.

> **참고:** **역사적 메모.** Linux 커널은 2.6 이전까지 비선점형이었고, 2.6(2003)부터 완전 선점형이 되었다. 현대 Linux, Windows, macOS는 모두 다수의 코어로 확장할 수 있도록 설계된 선점형 커널이다.

## 2. Peterson의 해법

### 2.1 알고리즘

Peterson의 해법은 **두 프로세스(P0, P1)** 를 위한 임계 구역 문제의 고전적인 **소프트웨어 전용** 해법이다. 다음 두 공유 변수를 사용한다.

```c
int     turn;       /* 누구의 차례인지 */
boolean flag[2];    /* flag[i] = true 이면 프로세스 i가 들어가고 싶어 함 */
```

각 프로세스 Pi(상대는 Pj, `j = 1 - i`)는 다음을 실행한다.

```c
while (true) {
    flag[i] = true;        /* 들어가고 싶다고 알림 */
    turn = j;              /* 양보: 너 먼저 */
    while (flag[j] && turn == j)
        ;                  /* 상대도 들어가려 하고, 상대 차례라면 대기 */

    /* critical section */

    flag[i] = false;       /* 끝났음을 알림 */

    /* remainder section */
}
```

직관적으로 **`flag[i]`** 는 Pi가 들어가고 싶다는 뜻이고, **`turn`** 은 상대에게 먼저 차례를 양보한다는 뜻이다. 프로세스는 상대가 들어가고 싶지 않거나(`flag[j] == false`) 상대가 이미 양보했을 때(`turn == i`) 임계 구역에 들어간다.

### 2.2 정확성 증명

**1. 상호 배제.** Pi가 진입 구역의 루프를 빠져나가려면 `flag[j] == false`이거나 `turn == i`여야 한다. 두 프로세스가 동시에 임계 구역에 있다면 `flag[0]`과 `flag[1]`이 모두 `true`이므로 둘 다 `turn` 조건으로만 빠져나왔어야 한다. 그런데 `turn`은 0 또는 1 중 하나의 값만 가지므로 `turn == 0`과 `turn == 1`이 동시에 성립할 수 없다. 모순이므로 상호 배제가 성립한다.

**2. 진행.** Pj가 잔여 구역에 있다면 `flag[j] == false`이므로 Pi는 곧바로 진입한다. Pj가 `flag[j] = true`로 설정하고 진입 구역에 있다면 `turn`이 결정한다. `turn`은 하나의 값만 가지므로 둘 중 정확히 하나가 들어간다.

**3. 한정 대기.** Pi가 대기 중이라고 하자. Pj가 임계 구역을 빠져나오면서 `flag[j] = false`로 설정하면 Pi가 들어간다. Pj가 다시 들어가려면 먼저 `turn = i`로 설정해야 하므로 Pi가 Pj보다 먼저 들어간다. 따라서 Pj는 Pi보다 **최대 1번**만 먼저 들어갈 수 있고, **상한은 1**이다.

> **참고:** **실용적으로 쓰이지 않는데도 Peterson의 해법이 유명한 이유.** 이 해법은 공유 메모리에 대한 **일반적인 load/store만으로**(이론적으로는 특별한 하드웨어 명령 없이) 상호 배제를 달성할 수 있음을 보인다. 이 이론적 명료함 덕분에 운영체제 교재에 널리 실린다.

### 2.3 현대 아키텍처에서의 한계

Peterson 해법의 정확성 증명은 명령이 **프로그램 순서대로** 실행되고 쓰기가 다른 CPU에 즉시 보인다고 가정한다. **현대 프로세서와 컴파일러는 두 가정을 모두 위반한다.** 성능을 위해 독립적인 load/store를 일상적으로 **재배열**하고, 쓰기가 코어별 쓰기 버퍼에 잠시 머문 뒤에야 전역적으로 보이기도 한다.

```text
/* Peterson 진입 구역 */
flag[i] = true;     /* ① */
turn = j;           /* ② */
```

CPU가 ②를 ①보다 먼저 실행하면 두 프로세스 모두 진입 검사를 통과해 임계 구역에 동시에 들어갈 수 있다. 즉 **상호 배제가 깨진다**. 두 쓰기는 서로 무관한 메모리를 다루므로 컴파일러의 재배열도 같은 효과를 낳을 수 있다.

![그림 2. Peterson 해법에서 명령어 재배열의 효과](../../images/Week09_Peterson-Reorder.png)

*그림 2. Peterson 해법에서 명령어 재배열의 효과*

그림 2(교재의 Figure 6.4)에서 process0은 재배열 때문에 `turn = 1`을 먼저 쓰고 `flag[0] = true`를 나중에 쓴다. 그 사이 process1이 `turn = 0`과 `flag[1] = true`를 쓰고, `flag[0]`이 아직 `false`이므로 임계 구역(cs)에 들어간다. 이어서 process0이 `flag[0] = true`를 쓰고 진입 검사를 하면 `turn`이 0이므로 대기하지 않고 임계 구역에 들어가, 두 프로세스가 동시에 임계 구역에 있게 된다.

**해결책:** 하드웨어와 컴파일러가 경계를 넘어 재배열하지 못하도록 **메모리 배리어**(3.1절)를 삽입한다. 적절한 배리어가 있으면 Peterson 알고리즘은 현대 하드웨어에서도 올바르게 동작한다. 다만 실무에서는 이런 복잡성을 숨기는 더 상위 수준의 기본 도구(락, 원자 변수)를 사용한다.

> **[컴퓨터구조]** **순차 일관성(sequential consistency)** 을 가정해 증명한 알고리즘도 **완화된 메모리 모델**을 쓰는 실제 하드웨어에서는 실패할 수 있다. 메모리 모델은 CPU와 컴파일러가 허용하는 load/store 재배열을 정의한다. x86은 TSO(total store order) 덕분에 비교적 강한 반면 ARM과 POWER는 더 많은 재배열을 허용한다. 동기화 코드는 **메모리 배리어**나 내부에 배리어를 넣는 상위 수준 도구로 이를 고려해야 한다.

## 3. 동기화를 위한 하드웨어 지원

### 3.1 메모리 배리어 (Memory Fence)

시스템의 **메모리 모델**은 메모리 연산이 여러 CPU 사이에서 어떻게 보이고 어떤 순서로 정렬되는지에 대해 하드웨어가 보장하는 내용을 기술한다.

- **강한 정렬(strongly ordered)**: 한 프로세서의 쓰기가 다른 모든 프로세서에 **즉시**, 프로그램 순서대로 보인다. 이해하기 쉽지만 느리다.
- **약한 정렬(weakly ordered)**: 쓰기가 **순서가 어긋나거나 지연된 채** 보일 수 있다. 빠르기 때문에 현대 멀티코어 설계의 주류이며, ARM이 대표적이고 x86도 일부 재배열(앞선 쓰기보다 나중 읽기가 먼저 수행되는 경우)을 허용한다.

**메모리 배리어(memory barrier)** 또는 **메모리 펜스(memory fence)** 는 **순서를 강제하는** 특수 명령이다. 다른 프로세서의 관점에서, 배리어 **이전**의 모든 load/store는 배리어 **이후**의 어떤 load/store보다 먼저 완료되어야 한다.

```c
/* Thread 1 */                       /* Thread 2 */
while (!flag)                        x = 100;
    ;                                memory_barrier();
memory_barrier();                    flag = true;
print x;  /* 반드시 100을 출력 */
```

배리어가 없으면 Thread 2의 `x` 쓰기가 `flag` 쓰기보다 **늦게** 보일 수 있고, 그러면 Thread 1은 `flag == true`인데 `x == 0`인 상태를 볼 수도 있다. 배리어는 프로그램 순서가 전역적으로도 유지되도록 강제한다.

- 메모리 배리어는 주로 **커널과 라이브러리 작성자**가 다루는 **매우 저수준**의 기본 도구이다. 대부분의 응용 프로그래머는 필요한 배리어를 내부에서 자동으로 삽입하는 락이나 원자 변수를 사용한다.
- 적절한 배리어가 있으면 **Peterson의 해법도 현대 하드웨어에서 올바르게 동작한다**.

> **[컴퓨터구조]** **메모리 배리어의 멘탈 모델.** 각 CPU 코어의 파이프라인과 캐시 일관성 메모리 시스템 사이에 **스토어 버퍼(store buffer)** 가 있다고 생각할 수 있다. `store` 명령어는 즉시 이 버퍼로 *리타이어*되어 파이프라인이 계속 진행할 수 있고, 버퍼는 나중에 하드웨어가 정하는 순서로 메모리에 드레인된다. 이 지연된 드레인 때문에 한 코어의 쓰기가 다른 코어에는 순서가 어긋나 보인다. 메모리 배리어(x86의 `mfence`/`sfence`, ARM의 `dmb`/`dsb`)는 다른 일을 하기 전에 자기 스토어 버퍼를 비우고 이후 연산이 이전 연산을 추월하지 못하게 하라는 명령이다.

### 3.2 test_and_set

`test_and_set`은 메모리 셀의 이전 값을 반환하면서 무조건 `true`를 쓰는 **원자(atomic)** 명령이다. 두 동작은 분할할 수 없는 단일 연산으로 수행된다.

```c
boolean test_and_set(boolean *target) {
    boolean rv = *target;
    *target = true;
    return rv;             /* 이전 값 */
}
```

**`test_and_set`으로 구현한 상호 배제**(lock의 초깃값은 `false`)는 다음과 같다.

```c
do {
    while (test_and_set(&lock))
        ;                  /* 반환된 이전 값이 false일 때까지 바쁜 대기 */

    /* critical section */

    lock = false;

    /* remainder section */
} while (true);
```

`test_and_set`을 처음 호출한 스레드는 `false`를 보고 값을 `true`로 바꾼 뒤 진입한다. 이후의 모든 호출자는 `true`를 보고 스핀한다. 두 CPU가 정확히 같은 순간 `test_and_set`을 호출하더라도 하드웨어가 두 호출을 **직렬화** 하므로 단 하나의 호출만 `false`를 읽는다.

### 3.3 compare_and_swap (CAS)

더 일반적인 원자 기본 연산인 **compare-and-swap**은 메모리 셀이 기대한 값을 가지고 있는지 원자적으로 확인하고, 그렇다면 새 값으로 교체한다.

```c
int compare_and_swap(int *value, int expected, int new_value) {
    int temp = *value;
    if (*value == expected)
        *value = new_value;
    return temp;           /* 항상 원래 값을 반환 */
}
```

**CAS를 이용한 상호 배제**(lock의 초깃값은 0이며, 0은 자유, 1은 점유)는 다음과 같다.

```c
while (true) {
    while (compare_and_swap(&lock, 0, 1) != 0)
        ;                  /* lock이 0이 될 때까지 스핀 */

    /* critical section */

    lock = 0;

    /* remainder section */
}
```

- Intel x86에서는 CAS를 **`lock cmpxchg`** 명령으로 구현한다. `cmpxchg`(compare-and-exchange) 명령 앞에 `lock` 접두사를 붙여 대상 피연산자를 갱신하는 동안 버스를 잠근다.
- CAS는 락-프리 큐 같은 현대 락-프리(lock-free) 자료 구조 대부분의 바탕이 되는 기본 연산이며, 위험 포인터(hazard pointer) 같은 메모리 회수 기법에도 쓰인다.

> **참고:** **CAS가 test_and_set보다 강력한 이유.** `test_and_set`은 boolean에서만 동작하지만, CAS는 임의의 정수에 대해 동작하며 값이 마지막으로 읽은 값과 여전히 같을 때만 갱신하는 연산을 표현할 수 있다. 이는 스레드가 값을 읽고 새 값을 계산한 뒤, 그 사이 다른 스레드가 값을 바꾸지 않은 경우에만 커밋하는 **낙관적 동시성(optimistic concurrency)** 의 토대이다.

### 3.4 CAS: 한정 대기 보장

위의 단순한 CAS 스핀 락은 상호 배제는 보장하지만 **한정 대기는 보장하지 않는다**. 운 나쁜 스레드가 계속 락을 빼앗길 수 있기 때문이다. 다음 확장은 `waiting[]` 플래그 배열을 사용하여, 모든 요청자가 다른 스레드의 임계 구역 진입을 최대 `n - 1`회 본 뒤에는 처리되도록 보장한다.

```c
/* 공유: boolean waiting[n] = {false}, int lock = 0 */

while (true) {
    waiting[i] = true;                          /* 대기 중임을 표시 */
    key = 1;
    while (waiting[i] && key == 1)
        key = compare_and_swap(&lock, 0, 1);    /* 락 시도 */
    waiting[i] = false;

    /* critical section */

    j = (i + 1) % n;
    while ((j != i) && !waiting[j])
        j = (j + 1) % n;                        /* 다음 대기자 탐색 */

    if (j == i)
        lock = 0;                               /* 대기자 없음 */
    else
        waiting[j] = false;                     /* 다음 대기자에게 락 양도 */

    /* remainder section */
}
```

스레드는 임계 구역을 빠져나올 때 자기 다음 인덱스부터 `waiting[]`을 **순환적으로** 탐색하여 처음 발견한 대기자에게 락을 넘긴다. 따라서 모든 요청자는 다른 진입을 최대 `n - 1`회 본 뒤 반드시 처리되며, 이것이 **한정 대기**이다.

### 3.5 원자 변수

**원자 변수(atomic variable)** 는 CAS 위에 만든 더 상위 수준의 추상으로, CAS 루프를 직접 작성하지 않고도 단일 정수에 대한 경쟁 조건 없는 갱신을 제공한다.

전형적인 CAS 기반 원자 증가는 다음과 같다.

```c
void increment(atomic_int *v) {
    int temp;
    do {
        temp = *v;
    } while (temp != compare_and_swap(v, temp, temp + 1));
}
```

그 사이 다른 스레드가 값을 바꾸었으면 CAS가 실패하고, 루프는 갱신된 값으로 다시 시도한다.

**Linux 커널 API:**

```c
atomic_t counter;
atomic_set(&counter, 5);                /* counter = 5  */
atomic_add(10, &counter);               /* counter = 15 */
atomic_sub(4, &counter);                /* counter = 11 */
atomic_inc(&counter);                   /* counter = 12 */
int val = atomic_read(&counter);        /* val     = 12 */
```

> **주의:** 원자 변수는 **단일 변수**의 갱신만 보호한다. 유한 버퍼의 `0 ≤ count ≤ n`과 `in`, `out` 인덱스처럼 여러 변수에 걸친 불변식에는 임계 구역 전체를 보호하는 **뮤텍스**나 **세마포어**가 필요하다.

> **참고:** **유용한 어림 규칙.** 카운터를 증가시키거나 플래그를 설정하는 것이 전부라면 원자 변수를 쓴다. 관련된 두 개 이상의 필드를 **함께** 갱신하여 어떤 관찰자도 둘이 어긋난 상태를 보지 못하게 해야 한다면 락을 쓴다.

## 4. 뮤텍스 락

### 4.1 뮤텍스 락: 기본

**뮤텍스 락**(**mut**ual **ex**clusion)은 가장 단순한 동기화 도구로, Boolean `available` 플래그와 두 연산으로 구성된다.

```c
acquire() {
    while (!available)
        ;                  /* 바쁜 대기 */
    available = false;
}

release() {
    available = true;
}
```

사용 패턴은 다음과 같다.

```c
acquire(lock);
    /* critical section */
release(lock);
```

교재의 정의가 드러내지 않는 요건은 두 가지이다.

- `acquire()`와 `release()` 자체가 **원자적**이어야 한다. 보통 `test_and_set`이나 CAS 위에 구현한다.
- 락 변수는 **Boolean**이며 정확히 두 상태(점유, 자유)를 가진다.

뮤텍스의 역할은 임계 구역이 마치 **고립되어 실행된 것처럼** 보이게 만드는 것이다.

### 4.2 스핀락과 바쁜 대기

**스핀락(spinlock)** 은 `acquire()`가 스레드를 잠재우지 않고 락이 풀릴 때까지 **바쁘게 대기(loop)** 하는 뮤텍스이다.

| 속성 | 스핀락 | Sleeping 락 |
|----------|----------|---------------|
| 대기 방식 | **스핀** (루프) | **블록** (sleep) |
| 깨어나는 비용 | 없음 (이미 실행 중) | 문맥 교환 2회 (sleep + wake) |
| 적합한 경우 | 락을 **매우 짧게** 잡는 경우 | 락을 **오래** 잡는 경우 |
| 위험 | 단일 프로세서에서 CPU 낭비, 다른 코어가 락을 풀 수 있는 멀티코어에서만 스핀이 생산적 | 락 획득 지연 |

*표 1. 스핀락과 sleeping 락의 비교*

**스핀락의 장점:**
- **문맥 교환 오버헤드가 없다.** 락이 풀리면 스핀 중인 스레드가 다음 루프 반복에서 곧바로 이를 확인하고 진행한다.
- **멀티코어 시스템에서 특히 유용하다.** 코어 A가 락을 잡고 있는 동안 코어 B는 생산적으로 스핀할 수 있고, A가 락을 풀자마자 스케줄러의 개입 없이 B가 락을 잡는다.
- **어림 규칙:** 예상 점유 시간이 **문맥 교환 2회보다 짧을 때** 스핀락을 사용한다.

**스핀락의 단점:**
- CPU 사이클을 낭비한다. 다른 유용한 일이 없는 **단일 프로세서**에서는 스핀이 순수한 낭비이다(스피너가 CPU를 점유하는 동안 락 점유자는 락을 풀 수 없다).
- 같은 락을 차지하려는 스레드가 많아 **락 경합(lock contention)** 이 심해지면 성능이 크게 떨어진다.

**락 경합 용어:**
- **무경합(uncontended) 락**: 한 스레드가 시도해 곧바로 획득하는 경우이다.
- **경합(contended, blocked) 락**: 여러 스레드가 동시에 시도해 일부가 기다려야 하는 경우이다.

> **참고:** **더 깊은 그림.** 스핀락과 sleeping 락의 선택은 *시간 비용*의 트레이드오프이다. Sleep은 문맥 교환 2회라는 고정 비용을 치르고, 스핀은 대기 시간에 비례하는 비용을 치른다. 더 작은 쪽이 유리하므로, 커널은 매우 짧은 커널 데이터 임계 구역에는 스핀락을, 더 긴 사용자 수준 작업에는 sleeping 락(뮤텍스)을 쓰는 경우가 많다.

## 5. 세마포어

### 5.1 정의 (wait / signal)

**세마포어(semaphore)** S는 두 **원자** 연산으로만 접근하는 정수 변수이며, Edsger Dijkstra가 처음 제안했다.

**`wait(S)`** 는 **P**(네덜란드어 *proberen*, "테스트하다")라고도 한다.

```c
wait(S) {
    while (S <= 0)
        ;          /* 바쁜 대기 */
    S--;
}
```

**`signal(S)`** 는 **V**(네덜란드어 *verhogen*, "증가시키다")라고도 한다.

```c
signal(S) {
    S++;
}
```

놓치기 쉬운 원자성 요건이 두 가지 있다.
- `S`의 변경(`S--`와 `S++`)은 read-modify-write로 분해되므로 원자적이어야 한다.
- `wait`에서는 **`S`의 테스트와 감소가 함께 분할 불가능** 해야 한다. 그렇지 않으면 두 스레드가 모두 `S = 1`을 보고 둘 다 감소시켜 `S = -1`이 되고, 한 스레드만 들어가야 할 상황에 두 스레드가 들어간다.

### 5.2 세마포어 종류와 활용

**계수형 세마포어(counting semaphore).**
- 범위는 음이 아닌 임의의 정수이다.
- **N개의 동일한 자원으로 이루어진 자원 풀**을 모델링한다.
- `wait(S)`는 자원 하나를 획득하고(S 감소), `signal(S)`는 자원 하나를 반환한다(S 증가).
- `S = 0`이면 모든 자원이 사용 중이므로 이후의 `wait()` 호출은 블록된다.

**이진 세마포어(binary semaphore).**
- 범위는 0 또는 1이다.
- **뮤텍스 락과 거의 같게** 동작한다. 1로 초기화하고 `wait`를 lock으로, `signal`을 unlock으로 쓴다.

**세마포어로 실행 순서 제어.** 세마포어는 한 문장이 다른 문장보다 먼저 실행되도록 강제할 수도 있다. `synch`를 0으로 초기화하면 다음과 같다.

```text
P1:                           P2:
    S1;                           wait(synch);
    signal(synch);                S2;
```

`P2`는 `P1`이 `S1`을 실행한 뒤 `signal(synch)`를 호출할 때까지 `wait(synch)`에서 블록된다. 따라서 P1과 P2가 어떤 순서로 스케줄되든 **S2는 반드시 S1 이후에 실행된다**.

> **핵심:** **뮤텍스 대비 일반화.** 계수형 세마포어는 **구별할 수 없는 자원이 N개** 있을 때(DB 커넥션, 스레드 풀 슬롯, 빈 버퍼 슬롯 등) 자연스러운 도구이다. 뮤텍스는 한 번에 하나의 접근만 허용하고, 계수형 세마포어는 한 번에 최대 N개의 접근을 허용한다.

### 5.3 바쁜 대기 제거 (대기 큐)

교재의 `wait()` 정의는 바쁜 대기를 하므로 임계 구역이 길면 낭비가 크다. 실제 구현은 각 세마포어에 블록된 프로세스의 **대기 큐(waiting queue)** 를 붙인다.

```c
typedef struct {
    int value;
    struct process *list;     /* 대기 큐 */
} semaphore;

wait(semaphore *S) {
    S->value--;
    if (S->value < 0) {
        /* 이 프로세스를 S->list에 enqueue */
        sleep();              /* 깨워질 때까지 블록 */
    }
}

signal(semaphore *S) {
    S->value++;
    if (S->value <= 0) {
        /* S->list에서 어떤 프로세스 P를 dequeue */
        wakeup(P);
    }
}
```

기억해 둘 결과는 두 가지이다.

- `S->value`가 **음수**일 때 그 **절댓값은 이 세마포어에 블록된 프로세스 수와 같다**.
- **FIFO** 대기 큐는 **한정 대기**를 보장한다(블록된 프로세스가 순서대로 깨어난다).

이 구현의 `wait`는 먼저 감소시킨 뒤 검사한다는 점에 주의할 필요가 있다. 이 순서가 위의 음수 값 부기와 맞아떨어진다.

### 5.4 세마포어 구현의 원자성

`wait()`와 `signal()`이 올바르게 동작하려면 그 본체가 **원자적으로** 실행되어야 한다.

- **단일 프로세서**: wait/signal 본체가 실행되는 동안 **인터럽트를 비활성화** 하면 된다. 저렴하고 효과적이다.
- **다중 프로세서**: 모든 CPU에서 인터럽트를 끄는 것은 비용이 크고 지연 시간에도 나쁘다. 구현은 내부에서 **CAS**나 **스핀락**을 사용해 코어 간에 wait/signal 본체를 원자적으로 만든다.

이 방법이 바쁜 대기를 **완전히 없애지는 않는다**. 응용의 잠재적으로 긴 임계 구역에서 하던 바쁜 대기를 wait/signal 내부의 짧은 몇 명령으로 줄일 뿐이다. 그래도 응용은 sleep/wakeup의 이점을 누린다. 응용 *자신의* 임계 구역은 더 이상 바쁜 대기를 요구하지 않기 때문이다.

> **참고:** **머릿속에 둘 그림.** 동기화 기본 도구는 **스택**을 이룬다. 맨 아래에 하드웨어(CAS, 펜스)가 있고, 그 위에 작은 내부 스핀락이, 그 위에 sleep/wake 인터페이스를 노출하는 세마포어가 있다. 각 층은 아래층의 바쁜 대기를 숨긴다.

## 6. 모니터

### 6.1 세마포어 사용의 어려움

세마포어는 강력하지만 **오류에 취약**하다. 잘못 쓰면 특정 인터리빙에서만 드러나는 타이밍 버그가 생겨 디버깅이 매우 어려워진다. 흔한 실수는 다음과 같다.

- **순서 뒤바꿈**: `signal(mutex); CS; wait(mutex);`로 쓰면 여러 프로세스가 동시에 임계 구역에 들어갈 수 있어 **상호 배제가 깨진다**.
- **wait 중복**: `wait(mutex); CS; wait(mutex);`로 쓰면 두 번째 `wait`에서 영원히 블록되어 **데드락**이 된다.
- **wait 또는 signal 누락**: 임계 구역이 보호되지 않거나 아무도 깨어나지 않는다.

이 버그들에는 세 가지 공통점이 있다. (1) 코드가 그럴듯해 보이고, (2) 보통 테스트를 통과하며, (3) 실패가 드물고 타이밍에 의존한다. 이를 줄이는 방법은 명시적인 `wait`/`signal` 호출을 감추는 **모니터(monitor)** 같은 상위 수준 구문을 사용하는 것이다.

### 6.2 모니터: 구조

**모니터**는 자신의 연산들 사이에 상호 배제를 자동으로 제공하는 **추상 자료형(ADT)** 이다. 어느 시점에도 모니터 안에서 실행 중인 스레드는 최대 하나이다.

```text
monitor monitor_name {
    /* 공유 변수 선언 (private) */

    function P1(...) { ... }
    function P2(...) { ... }
    ...
    function Pn(...) { ... }

    initialization_code(...) { ... }
}
```

![그림 3. 모니터의 도식적 구조](../../images/Week09_Monitor-Schematic.png)

*그림 3. 모니터의 도식적 구조*

그림 3(교재의 Figure 6.12)에서 모니터는 위쪽의 공유 데이터(shared data), 가운데의 연산들(operations), 아래쪽의 초기화 코드(initialization code)로 이루어지며, 모니터에 들어가려는 스레드는 바깥의 진입 큐(entry queue)에서 차례를 기다린다.

주요 속성은 다음과 같다.
- 모니터 안에서는 **한 번에 한 스레드**만 활성화될 수 있다. 각 함수에 락/언락을 삽입하는 일은 프로그래머가 아니라 컴파일러나 런타임이 맡는다.
- 내부 변수에는 **모니터의 함수를 통해서만** 접근할 수 있으므로 외부에서 손상시킬 방법이 없다.
- 프로그래머는 모니터 락을 위한 `wait(mutex)`/`signal(mutex)`를 작성하지 않는다.

> **참고:** **이것이 큰 도약인 이유.** 세마포어에서 상호 배제는 X를 건드리는 모든 코드가 먼저 wait를 호출해야 한다는 프로그래머 사이의 **약속**이다. 모니터에서 상호 배제는 ADT의 **구조적** 속성이다. 모니터 함수를 거치지 않고는 X에 접근할 길이 없고, 모니터 함수는 자동으로 보호된다.

### 6.3 조건 변수

상호 배제만으로는 충분하지 않은 경우가 있다. 모니터 안의 스레드가 다른 모니터 함수가 만들어 줄 **조건**을 기다려야 할 때이다. **조건 변수(condition variable)** 가 이 역할을 한다.

```text
condition x, y;

x.wait();      /* 호출한 스레드가 x에서 대기 */
x.signal();    /* x에서 대기 중인 스레드 하나를 깨움 */
```

세마포어와의 본질적인 차이는 두 가지이다.

- `x.signal()`은 `x`에서 대기 중인 스레드가 없으면 **아무 일도 하지 않는다**. 세마포어의 `signal`은 항상 값을 바꾼다.
- `x.wait()`를 호출한 스레드는 다른 스레드가 들어올 수 있도록 **모니터를 놓는다**. 그렇지 않으면 모니터가 데드락에 빠진다.

**`x.signal()` 이후 신호를 보낸 P와 깨어난 Q가 모두 모니터 안에 있으려 하면 어떻게 하는가?** 세 가지 정책이 있다.

- **Signal-and-wait**: P가 기다리고 Q가 즉시 실행된다(Hoare의 원래 정의).
- **Signal-and-continue**: P가 모니터를 떠날 때까지 계속 실행되고, 그다음에 Q가 실행된다.
- **타협안**: P는 신호 직후 모니터를 떠나고 Q가 재개된다.

![그림 4. 조건 변수가 있는 모니터](../../images/Week09_Monitor-Conditions.png)

*그림 4. 조건 변수가 있는 모니터*

그림 4(교재의 Figure 6.13)는 그림 3의 구조에서 공유 데이터 영역에 조건 x, y마다 대기 큐가 붙은 모습이다. `x.wait()`를 호출한 스레드는 x의 큐에서, `y.wait()`를 호출한 스레드는 y의 큐에서 기다린다.

> **참고:** **조건 변수가 있는 이유.** 조건 변수는 어떤 상태 변화(예: 버퍼가 비어 있지 않게 되는 것)를 기다리는 스레드가 **모니터를 양보**할 수 있게 하고, 다른 스레드가 그 상태를 바꾸었을 때 대기자를 **깨울** 수 있게 한다. 조건 변수가 없으면 대기 스레드는 스핀하여 CPU를 낭비하거나, 모니터 락을 잡은 채 블록되어 데드락에 빠진다.

### 6.4 세마포어로 모니터 구현

모니터는 세마포어 위에 만들 수 있다. 다음은 **signal-and-wait** 버전이다. 모든 외부 모니터 함수 `F`는 다음과 같이 감싼다.

```text
semaphore mutex      = 1;     /* 모니터 진입을 보호 */
semaphore next       = 0;     /* 신호자가 여기서 대기 */
int       next_count = 0;     /* next에 블록된 신호자 수 */

/* 모든 외부 함수 F의 본체 */
wait(mutex);
    ... F의 본체 ...
if (next_count > 0)
    signal(next);             /* 대기 중인 신호자 깨우기 */
else
    signal(mutex);            /* 아니면 모니터 락 해제 */
```

각 조건 변수 `x`에는 자기만의 세마포어 `x_sem`과 카운터 `x_count`가 필요하다.

```text
/* x.wait() */                          /* x.signal() */
x_count++;                              if (x_count > 0) {
if (next_count > 0)                         next_count++;
    signal(next);                            signal(x_sem);
else                                         wait(next);
    signal(mutex);                           next_count--;
wait(x_sem);                            }
x_count--;
```

부기는 복잡하지만 바로 그것이 *요점*이다. 모니터 추상은 이 복잡성을 프로그래머에게서 숨기고, 컴파일러나 런타임이 한 번만 정확히 구현하면 된다.

### 6.5 ResourceAllocator 모니터 예제

가장 **짧은** 시간을 요구하는 요청자에게 우선권을 주는 단일 자원 할당 모니터는 다음과 같다. `condition.wait(time)` 형태의 우선순위 대기를 사용한다.

```text
monitor ResourceAllocator {
    boolean   busy;
    condition x;

    void acquire(int time) {
        if (busy)
            x.wait(time);     /* time = 우선순위; 작을수록 먼저 */
        busy = true;
    }

    void release() {
        busy = false;
        x.signal();           /* 가장 작은 time을 가진 대기자를 깨움 */
    }

    initialization_code() {
        busy = false;
    }
}
```

사용법은 다음과 같다.

```text
R.acquire(t);
    ... 자원 사용 ...
R.release();
```

`x.wait(c)`는 호출자에게 우선순위 값 `c`를 저장하고, `x.signal()`은 저장된 값이 **가장 작은** 대기자를 재개한다. 이것은 일부 모니터 구현이 지원하는 **conditional-wait** 변형이다.

## 7. Liveness

**Liveness** 실패란 개별 프로세스는 살아 있지만 시스템이 그 프로세스들이 원하는 일을 결코 진행하지 못하는 상태이다. 상호 배제가 **안전성(safety)** 에 관한 성질이라면, liveness는 **결국 자기 차례를 얻는 것**에 관한 성질이다.

### 7.1 데드락

**데드락(deadlock)** 은 어떤 프로세스 집합의 모든 프로세스가 **그 집합 안의 다른 프로세스만이** 일으킬 수 있는 사건을 기다리는 상태이다. 어느 프로세스도 진행할 수 없다.

두 세마포어 S, Q(둘 다 1로 초기화)를 사용한 고전적인 두 프로세스 데드락은 다음과 같다.

```text
P0                          P1
wait(S);                    wait(Q);
wait(Q);                    wait(S);
...                         ...
signal(S);                  signal(Q);
signal(Q);                  signal(S);
```

P0이 S를 획득하고 `wait(Q)` 직전에 선점되고, P1이 Q를 획득하고 `wait(S)` 직전에 선점되면 **각자가 상대에게 필요한 것을 들고 있으므로** 어느 쪽도 진행할 수 없다.

- 데드락은 주로 **자원 획득과 해제** 주변에서 발생한다.
- 데드락의 진단, 예방, 회피, 탐지, 복구는 **10주차**에서 자세히 다룬다.

> **참고:** **데드락의 네 가지 필요 조건(10주차 미리보기).** 상호 배제, 점유 후 대기, 비선점, 순환 대기이다. 이 중 하나만 제거해도 데드락을 막을 수 있으므로, 무엇을 살펴야 하는지 알면 유용한 틀이 된다.

### 7.2 우선순위 역전과 우선순위 상속

**우선순위 역전(priority inversion)** 은 **낮은 우선순위** 프로세스가 간접적으로 **높은 우선순위** 프로세스를 **블록**시키는 미묘한 liveness 버그이다.

우선순위가 **L**(낮음) < **M**(중간) < **H**(높음)인 세 프로세스가 있다고 하자.

1. **L**이 세마포어 S를 획득한다.
2. **H**가 실행 가능 상태가 되어 S를 획득하려 하지만 블록되어 L을 기다린다.
3. **M**이 실행 가능 상태가 된다. M의 우선순위가 L보다 높으므로 M이 **L을 선점한다**.
4. M이 실행되는 동안 L은 S를 풀 수 없고, H는 진행할 수 없다.

결과적으로 H가 M보다 우선순위가 높은데도 **H는 M 때문에 지연된다**.

**우선순위 상속 프로토콜(Priority Inheritance Protocol):**
- L이 H가 기다리는 락을 들고 있는 동안 **L의 우선순위를 일시적으로 H 수준으로 올린다**.
- M은 더 이상 L을 선점할 수 없으므로 L이 임계 구역을 빨리 끝내고 S를 푼다.
- 락을 풀고 나면 L은 원래 우선순위로 돌아간다.

> **참고:** **유명한 실제 사건: Mars Pathfinder, 1997.** 화성 착륙선이 화성에서 원인을 알 수 없는 시스템 리셋을 반복했다. 원인은 **VxWorks RTOS**에서 일어난 우선순위 역전이었다. 낮은 우선순위의 기상 작업이 높은 우선순위의 버스 관리 작업에 필요한 뮤텍스를 들고 있었고, 중간 우선순위의 통신 작업이 낮은 우선순위 작업을 계속 선점했다. 그 결과 워치독 타이머가 만료되어 시스템을 리셋했다. JPL 엔지니어들은 문제의 뮤텍스에 **우선순위 상속을 활성화** 하여 원격으로 문제를 해결했다. 이 사건은 동기화 오류가 실제 시스템에 심각한 결과를 낳을 수 있음을 보여 준다.

### 7.3 동기화 도구 평가

동기화 도구의 **성능**은 **락 경합** 정도에 따라 달라진다.

| 경합 수준 | CAS 기반 (낙관적) | 락 기반 (비관적) |
|------------------|------------------------|-----------------------|
| **무경합** | 빠름 (약간 우세) | 빠름 |
| **중간** | **훨씬 빠름** (문맥 교환 없음) | 느림 (문맥 교환 비용) |
| **높음** | 느림 (CAS 재시도 다수) | 빠름 (큐 기반 정렬) |

*표 2. 경합 수준에 따른 CAS 기반 동기화와 락 기반 동기화의 성능*

추상 수준별로 분류하면 다음과 같다.

| 수준 | 도구 | 주 사용자 |
|-------|-------|--------------|
| **저수준** | 하드웨어 (CAS, test_and_set, 펜스) | 주로 더 상위 도구의 *기반*으로 사용 |
| **중간** | 뮤텍스 락, 세마포어 | 커널과 응용에서 가장 흔히 사용 |
| **고수준** | 모니터, 조건 변수 | 언어 수준 지원 (Java, C# `lock` 등) |

*표 3. 추상 수준별 동기화 도구*

> **참고:** **실용적 시사점.** 모든 상황에서 최고인 동기화 기본 도구는 없다. 올바른 선택은 **예상 경합**, **임계 구역의 길이**, 그리고 **다중 자원**과 **단일 플래그** 중 어느 의미가 필요한지에 따라 달라진다.

## 8. 동기화의 고전 문제들

세 가지 고전 문제는 시스템 소프트웨어 곳곳에서 반복해서 나타나며, 각각 고유한 동기화 패턴을 보여 준다.

### 8.1 유한 버퍼 문제

**크기가 n인 유한 버퍼**를 항목을 넣는 **생산자(producer)** 와 항목을 빼는 **소비자(consumer)** 가 공유한다. 세마포어 세 개를 사용한다.

| 세마포어 | 초깃값 | 역할 |
|-----------|------|------|
| `mutex` | 1 | 버퍼 보호 (이진). |
| `empty` | n | 빈 슬롯 수 (계수형). |
| `full`  | 0 | 채워진 슬롯 수 (계수형). |

*표 4. 유한 버퍼 문제의 세마포어와 초깃값*

공유 선언은 다음과 같다.

```c
int n;
semaphore mutex = 1;
semaphore empty = n;
semaphore full  = 0;
```

`empty`와 `full`은 **계수형** 세마포어이고, `mutex`는 버퍼 접근을 위한 **이진** 세마포어이다.

### 8.2 유한 버퍼: 생산자/소비자 코드

```c
/* Producer */                       /* Consumer */
while (true) {                       while (true) {
    /* 항목 생산 */                       wait(full);
                                         wait(mutex);
    wait(empty);
    wait(mutex);                         /* 버퍼에서 next_consumed로 */
                                         /* 항목 제거                */
    /* 버퍼에 항목 추가 */
                                         signal(mutex);
    signal(mutex);                       signal(empty);
    signal(full);
}                                        /* next_consumed 소비 */
                                     }
```

명백하지 않은 정확성 요점이 두 가지 있다.

- **wait 호출 순서가 중요하다.** 항상 `wait(mutex)` **이전에** `wait(empty)`나 `wait(full)`을 호출해야 한다. 생산자가 순서를 `wait(mutex); wait(empty);`로 바꾸면, 버퍼가 가득 찼을 때 생산자는 `mutex`를 든 채 `empty`에서 블록되고 소비자는 슬롯을 비우려 해도 `mutex`를 획득할 수 없다. 결과는 **데드락**이다.
- 생산자와 소비자는 **구조적으로 대칭**이다(`empty` ↔ `full`). 이런 패턴에서는 대칭을 확인하는 것이 가장 쉬운 정확성 검사인 경우가 많다.

> **참고:** **단일 뮤텍스가 아니라 세 세마포어를 쓰는 이유.** 단일 뮤텍스는 버퍼에 대한 상호 배제는 보장하지만, 생산자가 빈 슬롯이 생길 때까지 **기다리게** 만들 수는 없다. 두 계수형 세마포어가 슬롯의 *가용성*을 표현하고, 뮤텍스는 삽입과 제거 *행위*를 직렬화한다.

### 8.3 Readers-Writers 문제

공유 데이터셋에 두 종류의 프로세스가 접근한다.

- **읽기자(readers)**: 데이터를 읽기만 한다.
- **쓰기자(writers)**: 데이터를 읽고 수정한다.

동기화 규칙은 다음과 같다.

- **여러 읽기자는 동시에 읽을 수 있다**(서로 충돌하지 않는다).
- **쓰기자는 배타적 접근이 필요하다.** 다른 쓰기자도, 어떤 읽기자도 함께 접근할 수 없다.

문제의 두 변형은 어느 쪽을 우선하는가에 따라 달라진다.

- **첫 번째 Readers-Writers 문제(읽기자 우선).** 쓰기자가 대기 중이라도 읽기자는 들어갈 수 있다. 쓰기자가 **기아** 상태에 빠질 수 있다.
- **두 번째 Readers-Writers 문제(쓰기자 우선).** 쓰기자가 대기 중이면 새로운 읽기자는 들어갈 수 없다. 읽기자가 **기아** 상태에 빠질 수 있다.

두 버전 모두 **기아**가 가능하며 피해자만 다르다. **Reader-Writer 락**은 뮤텍스를 **읽기 모드(공유)** 와 **쓰기 모드(배타)** 로 구분할 수 있도록 일반화한 것이며, 우선순위 정책은 매개변수로 남긴다.

### 8.4 Readers-Writers: 첫 번째 문제 해법

공유 변수는 다음과 같다.

```c
semaphore rw_mutex = 1;     /* writer-vs-readers 배제 */
semaphore mutex    = 1;     /* read_count 보호       */
int       read_count = 0;
```

코드는 다음과 같다.

```c
/* Writer */                            /* Reader */
while (true) {                          while (true) {
    wait(rw_mutex);                         wait(mutex);
                                            read_count++;
    /* 쓰기 수행 */                          if (read_count == 1)
                                                wait(rw_mutex);
    signal(rw_mutex);                       signal(mutex);
}
                                            /* 읽기 수행 */

                                            wait(mutex);
                                            read_count--;
                                            if (read_count == 0)
                                                signal(rw_mutex);
                                            signal(mutex);
                                        }
```

프로토콜은 다음과 같이 동작한다.

- **첫 번째 읽기자**가 `rw_mutex`를 획득하여 쓰기자를 막고, 이후의 읽기자는 `rw_mutex`를 다시 획득하지 않는다.
- **마지막 읽기자**가 `rw_mutex`를 풀어 대기 중인 쓰기자가 들어올 수 있게 한다.
- `mutex`는 `read_count` 카운터만 보호하며 짧게만 잡힌다.

쓰기자가 임계 구역에 있고 n명의 읽기자가 대기 중이면, 읽기자 1명은 `rw_mutex`에서, 나머지 n − 1명은 `mutex`에서 대기한다. 쓰기자가 `signal(rw_mutex)`를 실행하면 대기 중인 읽기자들과 대기 중인 쓰기자 하나 중 어느 쪽을 재개할지는 스케줄러가 정한다.

### 8.5 Reader-Writer 락

**Reader-Writer 락**은 읽기와 쓰기의 구분을 1급 개념으로 만든 뮤텍스의 일반화이다.

- **읽기 모드**: 여러 스레드가 동시에 락을 잡을 수 있다.
- **쓰기 모드**: 한 스레드만 락을 잡을 수 있고, 그동안 어떤 읽기자도 락을 잡을 수 없다.

Reader-Writer 락은 다음 경우에 유리하다.
- 읽기 연산과 쓰기 연산이 코드에서 명확히 구분되는 경우이다.
- **읽기자가 쓰기자보다 압도적으로 많은** 경우이다. 더 복잡한 락의 비용을 읽기자들 사이의 더 높은 동시성으로 만회한다.

API 예시는 다음과 같다.
- POSIX: `pthread_rwlock_t`.
- Java: `java.util.concurrent.locks.ReentrantReadWriteLock`.
- Windows: **Slim Reader/Writer (SRW) Lock**.

### 8.6 식사하는 철학자들 문제

다섯 명의 철학자가 원형 식탁에 앉아 있다. 인접한 두 철학자 사이에는 젓가락이 하나씩 있어 모두 다섯 개이다. 각 철학자는 **사색**과 **식사**를 번갈아 하며, 식사를 하려면 **양쪽 젓가락을 모두 들어야** 한다.

규칙은 다음과 같다.
- 한 번에 하나의 젓가락만 집을 수 있다.
- 식사를 시작하려면 왼쪽과 오른쪽 젓가락이 모두 사용 가능해야 한다.
- 식사를 마치면 두 젓가락을 모두 내려놓는다.

![그림 5. 식사하는 철학자들](../../images/Week09_Dining-Philosophers.png)

*그림 5. 식사하는 철학자들*

그림 5(교재의 Figure 7.5)에서 원형 식탁 가운데에는 밥(rice) 그릇이 있고, 다섯 의자 앞에 각자의 접시가 놓여 있으며, 이웃한 두 접시 사이마다 젓가락이 하나씩 있다.

식사하는 철학자들 문제는 **여러 자원을 데드락이나 기아 없이 여러 프로세스에 할당하는 어려움**을 보여 주는 대표적인 예이다.

### 8.7 식사하는 철학자들: 세마포어 해법과 데드락

각 젓가락을 1로 초기화된 이진 세마포어로 표현한다.

```c
semaphore chopstick[5];   /* 모두 1로 초기화 */

/* 철학자 i */
while (true) {
    wait(chopstick[i]);              /* 왼쪽 */
    wait(chopstick[(i + 1) % 5]);    /* 오른쪽 */

    /* 잠시 식사 */

    signal(chopstick[i]);
    signal(chopstick[(i + 1) % 5]);

    /* 잠시 사색 */
}
```

이 해법은 **올바르지 않다**. 다섯 철학자가 동시에 `wait(chopstick[i])`를 실행하면(각자 왼쪽 젓가락을 집으면) 모든 젓가락 값이 0이 되고, 각 철학자는 `wait(chopstick[(i+1)%5])`에서 블록된다. **순환 대기로 데드락**이 발생하여 누구도 식사할 수 없다.

### 8.8 식사하는 철학자들: 데드락 회피 전략

고전적인 해결책은 세 가지이다.

- **방법 1: 동시에 식탁에 앉는 철학자를 최대 4명으로 제한한다.** 4로 초기화한 세마포어 `seats`를 추가한다. 최대 4명이 5개의 젓가락을 두고 경쟁하므로 항상 적어도 한 명은 양쪽 젓가락을 들 수 있다.
- **방법 2: 양쪽 젓가락이 모두 사용 가능할 때만 집는다.** 검사와 집기를 하나의 임계 구역에서 수행해 어떤 철학자도 한쪽만 들고 있지 않게 한다. 모니터 해법이 이 방식이다.
- **방법 3: 비대칭 프로토콜을 쓴다.** 홀수 번 철학자는 **왼쪽 먼저**, 짝수 번 철학자는 **오른쪽 먼저** 집는다. 이 방법은 **순환 대기** 조건을 깬다(데드락의 네 가지 조건은 10주차에서 다룬다).

> **주의:** **데드락이 없다고 해서 기아가 없는 것은 아니다.** 양쪽 이웃이 매우 배고픈 철학자는 원리적으로 영영 먹지 못할 수도 있다. 기아를 없애려면 추가적인 공정성 메커니즘이 필요하다.

### 8.9 식사하는 철학자들: 모니터 해법

모니터 해법은 양쪽 젓가락이 모두 사용 가능할 때만 집는다는 규칙을 구조적으로 강제되는 불변식으로 만든다.

```text
monitor DiningPhilosophers {
    enum {THINKING, HUNGRY, EATING} state[5];
    condition self[5];

    void pickup(int i) {
        state[i] = HUNGRY;
        test(i);
        if (state[i] != EATING)
            self[i].wait();
    }

    void putdown(int i) {
        state[i] = THINKING;
        test((i + 4) % 5);    /* 왼쪽 이웃 재확인 */
        test((i + 1) % 5);    /* 오른쪽 이웃 재확인 */
    }

    void test(int i) {
        if (state[(i + 4) % 5] != EATING &&
            state[i] == HUNGRY &&
            state[(i + 1) % 5] != EATING) {
            state[i] = EATING;
            self[i].signal();
        }
    }

    initialization_code() {
        for (int i = 0; i < 5; i++)
            state[i] = THINKING;
    }
}
```

각 철학자 i는 다음과 같이 모니터를 호출한다.

```text
DiningPhilosophers.pickup(i);
    ...
    /* 식사 */
    ...
DiningPhilosophers.putdown(i);
```

동작 방식은 다음과 같다.

- `pickup(i)`는 상태를 HUNGRY로 바꾸고 `test(i)`를 호출한다. 두 이웃이 모두 EATING이 아니면 상태가 EATING이 되고 철학자가 진행한다. 그렇지 않으면 `self[i].wait()`가 철학자를 블록시킨다.
- `putdown(i)`는 상태를 THINKING으로 바꾸고 두 이웃에 대해 다시 `test()`를 호출한다. 어느 이웃이 배고프고 그 이웃의 양옆 철학자가 식사 중이 아니면 그 이웃의 wait에 신호를 보낸다.
- **데드락이 없다.** 철학자는 **양쪽** 젓가락이 모두 사용 가능할 때만 식사하므로 누구도 한쪽만 들고 있지 않다.
- **기아는 가능하다.** 이웃들이 계속 번갈아 식사하면 운 나쁜 철학자는 계속 건너뛰어질 수 있다(교재의 연습 문제로 남겨져 있다).

## 9. 실제 시스템에서의 동기화

### 9.1 Windows 동기화

Windows는 단일 프로세서와 다중 프로세서의 경우를 구분하며, 커널 측과 사용자 측 기본 도구를 모두 제공한다.

- **단일 프로세서**: 커널에서 **인터럽트 마스킹**으로 전역 상태를 보호한다.
- **다중 프로세서**: 매우 짧은 커널 임계 구역에는 **스핀락**을 사용한다. 스레드는 스핀락을 들고 있는 동안 **선점되지 않는다**(그렇지 않으면 점유자가 잠든 사이 스피너가 오랫동안 CPU를 낭비하게 된다).

**Dispatcher Objects**는 사용자 스레드에 노출되는 동기화용 커널 객체이다.
- 예로 **Mutex Lock**, **Semaphore**, **Event**, **Timer**가 있다.
- 각 객체는 **signaled**(사용 가능)와 **nonsignaled**(사용 중)의 두 상태를 가진다.
- nonsignaled 객체를 요청한 스레드는 **블록**되어 객체의 대기 큐에 들어간다.
- 객체가 signaled 상태가 되면 객체 종류에 따라 대기 스레드 하나(뮤텍스) 또는 여럿(이벤트)이 **ready** 상태로 옮겨진다.

**Critical-Section Object**는 흔한 경우에 맞게 최적화한 사용자 모드 뮤텍스이다.
- 먼저 **스핀락**으로 획득을 시도하여 커널 호출을 피한다.
- 스핀이 너무 길어지면 **커널 뮤텍스**를 할당하고 블록한다.
- **무경합**인 경우 획득과 해제가 모두 사용자 모드에서 일어나므로 매우 빠르다.

### 9.2 Linux 동기화

Linux는 커널 **2.6**부터 **완전 선점형**이다(그 이전에는 비선점형).

| 도구 | 목적 | 비고 |
|------|---------|-------|
| `atomic_t`     | 원자 정수 연산 | 카운터, 시퀀스 생성기 |
| `spinlock_t`   | 짧은 커널 임계 구역 (SMP) | 단일 프로세서에서는 **선점 비활성화**로 대체 |
| `mutex`        | 더 긴 임계 구역 | **Sleeping** 락 (스핀하지 않고 블록) |
| `semaphore`    | 계수형 세마포어 | 긴 대기에 적합 |

*표 5. Linux 커널의 동기화 도구*

단일 CPU와 SMP에서 스핀락 기본 동작은 다음과 같이 다르다.

```c
/* 단일 프로세서                | 다중 프로세서          */
/* 커널 선점 비활성화           | 스핀락 획득            */
/* ... 임계 구역 ...                                   */
/* 커널 선점 활성화             | 스핀락 해제            */
```

Linux 스핀락과 뮤텍스의 중요한 속성은 두 가지이다.

- **비재귀(nonrecursive)**: 이미 락을 잡고 있는 스레드가 같은 락을 다시 잡으려 하면 **데드락**이 된다.
- 커널은 작업마다 `preempt_count`를 유지하며, `preempt_count == 0`일 때만 선점을 허용한다. 스핀락을 잡으면 이 카운터가 증가하고, 풀면 감소한다.

### 9.3 POSIX 뮤텍스 락

POSIX(UNIX, Linux, macOS)는 `pthread`를 통해 **사용자 수준**의 동기화 기본 도구를 제공한다.

```c
#include <pthread.h>

pthread_mutex_t mutex;
pthread_mutex_init(&mutex, NULL);

pthread_mutex_lock(&mutex);
    /* critical section */
pthread_mutex_unlock(&mutex);
```

이것은 pthread 프로그램에서 흔히 볼 수 있는 표준 뮤텍스 관용구이다.

### 9.4 POSIX 세마포어 (Named/Unnamed)

POSIX는 공유 범위가 다른 두 종류의 세마포어를 제공한다.

**Named 세마포어**는 문자열 이름으로 식별되며 **서로 무관한 프로세스들** 사이에서 공유될 수 있다.

```c
#include <semaphore.h>

sem_t *sem;
sem = sem_open("SEM", O_CREAT, 0666, 1);

sem_wait(sem);
    /* critical section */
sem_post(sem);
```

**Unnamed 세마포어**는 `sem_init(&sem, 0, 1)`로 초기화하며, **같은 프로세스 안의 스레드들**(또는 공유 메모리를 통한 관련 프로세스들) 사이에서 공유된다.

| 종류 | API | 공유 범위 |
|------|-----|---------------|
| Named   | `sem_open` / `sem_wait` / `sem_post` | **무관한 프로세스들** 간 |
| Unnamed | `sem_init` / `sem_wait` / `sem_post` | **단일 프로세스 내** (또는 공유 메모리 경유) |

*표 6. POSIX named 세마포어와 unnamed 세마포어의 비교*

### 9.5 POSIX 조건 변수

C에는 모니터가 내장되어 있지 않으므로 POSIX의 조건 변수는 뮤텍스와 명시적으로 짝지어 사용한다.

설정은 다음과 같다.

```c
pthread_mutex_t  mutex;
pthread_cond_t   cond_var;
pthread_mutex_init(&mutex, NULL);
pthread_cond_init(&cond_var, NULL);
```

대기하는 스레드의 코드는 다음과 같다.

```c
pthread_mutex_lock(&mutex);
while (a != b)
    pthread_cond_wait(&cond_var, &mutex);   /* 원자적: 뮤텍스 해제 + sleep */
pthread_mutex_unlock(&mutex);
```

신호를 보내는 스레드의 코드는 다음과 같다.

```c
pthread_mutex_lock(&mutex);
a = b;
pthread_cond_signal(&cond_var);             /* 한 명의 대기자 깨움 */
pthread_mutex_unlock(&mutex);
```

pthread 프로그래머가 알아야 할 규칙은 세 가지이다.

- `pthread_cond_wait()`는 **원자적으로 뮤텍스를 해제하고 블록**한다. 깨어나면 뮤텍스를 **다시 획득** 한 뒤 반환한다.
- `pthread_cond_signal()`은 뮤텍스를 해제하지 **않는다**. 신호를 보낸 스레드가 직접 `unlock()`을 호출해야 한다.
- 조건 검사는 `if`가 아니라 항상 **`while`** 루프 안에서 해야 한다. 표준은 spurious wakeup(가짜 깨어남)을 허용하며, 깨어난 뒤 뮤텍스를 다시 잡는 사이 다른 스레드가 상태를 바꾸었을 수 있다.

> **참고:** **"항상 while, 절대 if" 규칙.** `if (a != b) pthread_cond_wait(...)`라고 쓰는 것은 고전적인 버그이다. spurious wakeup이 일어나지 않더라도, 깨어난 스레드가 조건을 다시 검사하기 전에 다른 대기자가 자원을 먼저 가져갈 수 있고, 그러면 잘못된 전제로 진행하게 된다. `while`은 깨어날 때마다 술어를 다시 검사한다.

## 10. Java 동기화

Java는 모니터와 비슷한 동기화를 **언어 수준**에서 제공한다. `synchronized` 키워드가 주된 도구이고, `java.util.concurrent`에 더 풍부한 기본 도구가 있다.

### 10.1 Java 모니터: `synchronized`, `wait()`/`notify()`

Java의 내장 모니터를 사용한 유한 버퍼는 다음과 같다.

```java
public class BoundedBuffer<E> {
    private static final int BUFFER_SIZE = 5;
    private int count, in, out;
    private E[] buffer;

    public synchronized void insert(E item) {
        while (count == BUFFER_SIZE) {
            try { wait(); }
            catch (InterruptedException ie) { }
        }
        buffer[in] = item;
        in = (in + 1) % BUFFER_SIZE;
        count++;
        notify();
    }

    public synchronized E remove() {
        while (count == 0) {
            try { wait(); }
            catch (InterruptedException ie) { }
        }
        E item = buffer[out];
        out = (out + 1) % BUFFER_SIZE;
        count--;
        notify();
        return item;
    }
}
```

`synchronized` 키워드는 메소드에 진입할 때 수신 객체의 모니터 락을 **자동으로** 획득하고, 종료할 때(예외가 발생해도) 해제한다.

### 10.2 Java 모니터의 내부 동작

- 모든 Java 객체는 **하나의 락**, **entry set**(락을 기다리는 스레드들), **wait set**(`wait()`에서 블록된 스레드들)을 가진다.

**스레드가 `wait()`를 호출하면:**
1. 객체의 락을 해제한다.
2. **blocked** 상태로 전이한다.
3. **wait set**에 들어간다.

**스레드가 `notify()`를 호출하면:**
1. wait set에서 **임의의** 스레드 T를 선택한다.
2. T를 wait set에서 **entry set**으로 옮긴다.
3. T를 runnable로 표시한다.
4. T가 나중에 락을 다시 획득하면 T의 `wait()` 호출이 반환된다.

`notifyAll()`은 `notify()`와 같지만 wait set의 **모든** 스레드에 대해 동작한다. 같은 락을 공유하는 대기 조건이 두 종류 이상이면 `notifyAll()`을 사용한다. 그러면 조건이 실제로 만족된 스레드만 `while` 루프를 빠져나간다.

### 10.3 ReentrantLock과 Semaphore

`java.util.concurrent.locks.ReentrantLock`은 `synchronized`보다 유연한 락이다.

```java
Lock key = new ReentrantLock();
key.lock();
try {
    /* critical section */
} finally {
    key.unlock();    /* finally에서 반드시 해제 */
}
```

주요 기능은 다음과 같다.
- **공정성 매개변수**(`new ReentrantLock(true)`)를 주면 락이 가장 오래 기다린 스레드를 우선한다.
- **재진입 가능(reentrant)**: 이미 락을 잡고 있는 스레드는 데드락 없이 락을 다시 잡을 수 있다(락이 중첩 깊이를 센다).

> **[컴퓨터프로그래밍]** Java의 `try`-`catch`-`finally` 문에서 `finally` 블록은 `try` 블록이 정상적으로 끝나든 예외로 빠져나가든 항상 실행된다. 그래서 `lock()` 뒤의 임계 구역을 `try`로 감싸고 `unlock()`을 `finally`에 두면 임계 구역에서 예외가 발생해도 락이 해제되어, 락을 쥔 스레드가 사라진 뒤 다른 스레드가 영원히 기다리는 일을 막는다. 예제마다 있는 `catch (InterruptedException ie)` 절은 `wait()`, `acquire()`, `await()`가 던지는 검사 예외(checked exception)를 처리한다. 이 예외는 대기 중인 스레드가 인터럽트되었음을 알리며, Java 컴파일러는 검사 예외를 처리하거나 선언하도록 강제한다.

`java.util.concurrent.Semaphore`는 표준 세마포어이다.

```java
Semaphore sem = new Semaphore(1);
try {
    sem.acquire();
    /* critical section */
} catch (InterruptedException ie) { }
finally {
    sem.release();
}
```

### 10.4 Java 조건 변수

`Lock`과 연관된 `Condition` 객체를 쓰면 **이름 있는** 조건에서 대기할 수 있으므로, `notify()`처럼 임의의 스레드를 깨우는 대신 *특정* 대기자를 깨울 수 있다.

```java
Lock lock = new ReentrantLock();
Condition[] condVars = new Condition[5];
for (int i = 0; i < 5; i++)
    condVars[i] = lock.newCondition();

public void doWork(int threadNumber) {
    lock.lock();
    try {
        if (threadNumber != turn)
            condVars[threadNumber].await();

        /* 작업 수행 */

        turn = (turn + 1) % 5;
        condVars[turn].signal();
    } catch (InterruptedException ie) { }
    finally {
        lock.unlock();
    }
}
```

- `await()`는 락을 해제하고 블록한다(`pthread_cond_wait()`, Java `Object.wait()`에 대응한다).
- `signal()`은 그 이름 있는 조건에서 대기하는 **특정** 대기자를 깨운다. 이것이 내장 모니터의 단일 익명 `notify()`에 비해 갖는 주된 장점이다.

> **참고:** **이름 있는 조건 변수가 중요한 경우.** 유한 버퍼에서는 버퍼가 가득 차지 않았다는 조건과 버퍼가 비어 있지 않다는 조건이 별개이다. 단일 익명 `notify()`로는 마지막 슬롯을 채운 생산자가 빈 슬롯을 기다리는 다른 *생산자*를 깨울 수 있고, 그 생산자는 곧바로 다시 블록되어 깨움이 헛되게 된다. 이름 있는 조건 변수를 쓰면 생산자가 소비자의 조건에 정확히 신호를 보낼 수 있어 헛된 왕복이 사라진다.

## 11. 실습: 식사하는 철학자들 구현

이 절은 POSIX 스레드로 식사하는 철학자들 문제를 구현하며 앞에서 다룬 개념을 코드로 확인한다.

### 11.1 실습: 단순 pthread 구현

각 젓가락은 `pthread_mutex_t`이고, 각 철학자는 사색, 왼쪽 젓가락 잡기, 오른쪽 젓가락 잡기, 식사, 내려놓기를 반복하는 스레드이다.

```c
#include <pthread.h>
#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>
#define N 5

pthread_mutex_t chopstick[N];

void *philosopher(void *arg) {
    int id = *(int *)arg;
    while (1) {
        printf("Philosopher %d is thinking\n", id);
        usleep(rand() % 1000000);

        pthread_mutex_lock(&chopstick[id]);
        pthread_mutex_lock(&chopstick[(id + 1) % N]);

        printf("Philosopher %d is eating\n", id);
        usleep(rand() % 1000000);

        pthread_mutex_unlock(&chopstick[id]);
        pthread_mutex_unlock(&chopstick[(id + 1) % N]);
    }
    return NULL;
}
```

이 구현의 동작은 다음과 같다.
- 프로그램을 실행하면 모든 철학자가 왼쪽 젓가락을 들고 있는 상황에서 **데드락**에 빠질 수 있다.
- 고전적인 해결책 중 하나(비대칭 프로토콜, 최대 4명 제한, 모니터)를 구현하면 데드락이 사라진다.

### 11.2 실습: 비대칭(Asymmetric) 해법

짝수 번 철학자는 **오른쪽** 젓가락을 먼저, 홀수 번 철학자는 **왼쪽** 젓가락을 먼저 집는다. 이렇게 하면 순환 대기 조건이 깨진다.

```c
void *philosopher_asymmetric(void *arg) {
    int id = *(int *)arg;
    int first, second;

    if (id % 2 == 0) {
        first  = (id + 1) % N;     /* 오른쪽 먼저 */
        second = id;
    } else {
        first  = id;               /* 왼쪽 먼저 */
        second = (id + 1) % N;
    }

    while (1) {
        printf("Philosopher %d is thinking\n", id);
        usleep(rand() % 1000000);

        pthread_mutex_lock(&chopstick[first]);
        pthread_mutex_lock(&chopstick[second]);

        printf("Philosopher %d is eating\n", id);
        usleep(rand() % 1000000);

        pthread_mutex_unlock(&chopstick[first]);
        pthread_mutex_unlock(&chopstick[second]);
    }
    return NULL;
}
```

> **참고:** **비대칭 해법이 동작하는 이유.** 데드락에는 P0이 P1의 젓가락을, P1이 P2의 젓가락을, ..., P4가 P0의 젓가락을 기다리는 *사이클*이 필요하다. 비대칭 프로토콜에서는 홀수 번 철학자와 그 오른쪽의 짝수 번 철학자가 둘 사이의 젓가락을 모두 두 번째로 집는다. 이 젓가락을 쥔 철학자는 이미 첫 번째 젓가락을 들고 있으므로 식사할 수 있고, 따라서 사이클이 닫힐 수 없다.

### 11.3 실습: POSIX 조건 변수 기반 모니터 해법

8.9절의 교재 모니터를 POSIX로 직접 옮기면 다음과 같다.

```c
#include <pthread.h>
#define N 5

enum {THINKING, HUNGRY, EATING} state[N];
pthread_mutex_t monitor_lock = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  self[N];

void test(int i) {
    if (state[(i + 4) % N] != EATING &&
        state[i] == HUNGRY &&
        state[(i + 1) % N] != EATING) {
        state[i] = EATING;
        pthread_cond_signal(&self[i]);
    }
}

void pickup(int i) {
    pthread_mutex_lock(&monitor_lock);
    state[i] = HUNGRY;
    test(i);
    while (state[i] != EATING)
        pthread_cond_wait(&self[i], &monitor_lock);
    pthread_mutex_unlock(&monitor_lock);
}

void putdown(int i) {
    pthread_mutex_lock(&monitor_lock);
    state[i] = THINKING;
    test((i + 4) % N);
    test((i + 1) % N);
    pthread_mutex_unlock(&monitor_lock);
}
```

`pthread_cond_wait` 주변에 `while (state[i] != EATING)`을 사용한 점에 주목할 필요가 있다. 9.5절의 패턴 그대로이며 spurious wakeup을 방어한다.

| Java | `synchronized`와 `wait`/`notify(All)`, `ReentrantLock`(공정성, 재진입), `Semaphore`, 이름 있는 `Condition`을 제공한다. |

## 점검 문제

1. **경쟁 조건:** 경쟁 조건을 정의하고 생산자/소비자의 `count++`/`count--` 예시로 설명하라. 증상이 타이밍에 의존하는 이유는 무엇인가?

   <details>
   <summary>정답</summary>

   경쟁 조건은 둘 이상의 스레드가 공유 데이터에 동시에 접근하고 **결과가 인터리빙 순서에 따라 달라지는** 경우이다. `count = 5`일 때 `count++`와 `count--`는 각각 load → modify → store로 분해되며, 한 스레드의 store가 다른 스레드의 store를 덮어쓰는 인터리빙에서는 갱신 하나가 사라져 `count`가 `5` 대신 `4` 또는 `6`이 된다. 나쁜 인터리빙이 일어나는지는 스케줄링에 달려 있으므로 버그가 간헐적으로 나타나 테스트에서 놓치기 쉽다.

   </details>

2. **임계 구역 문제의 세 요건:** 임계 구역 문제의 세 요건을 말하라. 각 요건이 빠지면 어떤 일이 생기는가?

   <details>
   <summary>정답</summary>

   **상호 배제**는 임계 구역에 한 번에 한 프로세스만 들어가게 하며, 없으면 경쟁 조건이 생긴다. **진행**은 임계 구역이 비었을 때 들어가려는 프로세스 중 하나를 무기한 미루지 않고 선택하는 성질이며, 없으면 임계 구역이 비어 있는데도 아무도 들어가지 못하는 데드락이 생길 수 있다. **한정 대기**는 대기 프로세스가 진입하기 전에 다른 프로세스가 들어갈 수 있는 횟수를 제한하며, 없으면 기아가 생길 수 있다.

   </details>

3. **선점형과 비선점형 커널:** 선점형 커널과 비선점형 커널을 비교하라. 다중 프로세서 선점형 커널이 단일 CPU 비선점형 커널보다 더 신중한 동기화를 필요로 하는 이유는 무엇인가?

   <details>
   <summary>정답</summary>

   **단일 CPU 비선점형** 커널에서는 현재 스레드가 양보할 때까지 다른 커널 스레드가 실행될 수 없으므로 커널 데이터에 대한 경쟁 조건이 본질적으로 생기지 않는다. **선점형** 커널에서는 다른 스레드가(다른 **코어**에서도) 언제든 끼어들 수 있으므로 모든 공유 커널 구조에 명시적인 보호가 필요하다. 인터럽트 비활성화는 단일 프로세서에서는 충분하지만 SMP의 코어 사이에서는 충분하지 않다.

   </details>

4. **Peterson 해법:** Peterson 해법이 상호 배제를 만족하는 이유와 현대 하드웨어에서 깨질 수 있는 이유를 설명하라.

   <details>
   <summary>정답</summary>

   각 프로세스 Pi는 `flag[i] = true`, `turn = j`를 차례로 설정한 뒤 `flag[j] && turn == j`인 동안 대기한다. **상호 배제**: 두 프로세스가 모두 임계 구역 안에 있다면 `flag[0]`과 `flag[1]`이 모두 `true`이므로 둘 다 `turn`이 자기 번호일 때만 빠져나올 수 있었다. 그러나 `turn`은 하나의 값만 가지므로 모순이다. **현대 하드웨어**는 `flag[i] = true`와 `turn = j`의 쓰기를 재배열할 수 있고, `turn = j`가 먼저 보이면 두 프로세스 모두 진입 검사를 통과할 수 있다. 해결책은 두 쓰기 사이에 메모리 배리어를 넣는 것이다.

   </details>

5. **test_and_set과 CAS:** `test_and_set`과 `compare_and_swap`의 의사코드를 쓰고, 각각으로 락을 구현하는 방법을 보여라. CAS가 더 강력한 이유는 무엇인가?

   <details>
   <summary>정답</summary>

   - `test_and_set(target)`은 `*target`을 원자적으로 읽고 `true`로 설정한 뒤 이전 값을 반환한다. 락은 `test_and_set(&lock)`이 `true`를 반환하는 동안 스핀한다.
   - `compare_and_swap(value, expected, new_value)`는 `*value == expected`일 때만 원자적으로 `new_value`를 쓰고 원래 값을 반환한다. 락은 `compare_and_swap(&lock, 0, 1) != 0`인 동안 스핀한다.
   - CAS는 boolean뿐 아니라 **임의의 정수**에서 동작하고, 마지막으로 읽은 뒤 값이 바뀌지 않았을 때만 갱신하는 연산을 표현할 수 있다. 이 성질이 낙관적 동시성과 락-프리 자료 구조의 토대이므로 CAS가 더 강력하다.

   </details>

6. **원자 변수:** 원자 변수란 무엇이며, 어떤 용도에 **부적합**한가?

   <details>
   <summary>정답</summary>

   원자 변수는 보통 CAS 위에 만들어지며 **단일 변수**에 대한 경쟁 조건 없는 갱신(예: `atomic_inc(&counter)`)을 제공한다. 여러 변수에 걸친 불변식에는 **부적합** 하다. 예를 들어 유한 버퍼의 `count`, `in`, `out`은 함께 갱신되어야 하므로 하나의 뮤텍스나 세마포어로 보호하지 않으면 관찰자가 비일관적인 상태를 볼 수 있다.

   </details>

7. **스핀락과 sleeping 뮤텍스:** 스핀락과 sleeping 뮤텍스를 비교하라. 각각이 더 적합한 경우와 어림 규칙은 무엇인가?

   <details>
   <summary>정답</summary>

   **스핀락**은 바쁜 루프로 기다리고, **sleeping 뮤텍스**는 블록한다(문맥 교환 2회). 스핀락은 락을 매우 짧게 잡을 때, 특히 한 코어가 임계 구역을 끝내는 동안 다른 코어가 스핀할 수 있는 멀티코어 시스템에서 유리하다. Sleeping 락은 잠든 대기자가 자기 CPU를 내주므로 오래 잡는 락에 유리하다. **어림 규칙**은 예상 점유 시간이 **문맥 교환 2회보다 짧을 때** 스핀락을 쓰는 것이다.

   </details>

8. **세마포어 연산:** 세마포어의 `wait`와 `signal` 연산을 쓰라. 두 연산이 원자적이어야 하는 이유는 무엇인가?

   <details>
   <summary>정답</summary>

   `wait(S)`는 `S <= 0`인 동안 스핀한 뒤 `S--`를 수행하고, `signal(S)`는 `S++`를 수행한다. `S`의 테스트와 갱신이 분할할 수 없는 한 단계로 일어나야 하므로 원자적이어야 한다. 그렇지 않으면 두 스레드가 모두 `S = 1`을 읽고 둘 다 감소시켜 둘 다 진입했다고 판단하며, `S = -1`이 되고 두 스레드가 동시에 임계 구역에 있게 된다.

   </details>

9. **대기 큐 세마포어의 음수 값:** 대기 큐로 구현한 세마포어에서 `S->value`가 **음수**라는 것은 무엇을 뜻하는가?

   <details>
   <summary>정답</summary>

   그 절댓값이 **세마포어에 블록된 프로세스 수와 같다**는 뜻이다. 각 `wait`는 먼저 감소시키고 결과가 음수이면 호출자를 큐에 넣는다. 각 `signal`은 증가시키고 결과가 0 이하이면 큐에서 하나를 꺼내 깨운다.

   </details>

10. **세마포어 오용:** 흔한 세마포어 오용 버그 세 가지를 나열하라. 이 버그들을 디버깅하기 어려운 이유는 무엇인가?

    <details>
    <summary>정답</summary>

    `signal(mutex); CS; wait(mutex)`처럼 순서를 뒤집으면 여러 스레드가 임계 구역에 들어간다. `wait(mutex); CS; wait(mutex)`처럼 `wait`를 중복하면 두 번째 호출에서 데드락이 발생한다. `wait`나 `signal`을 빠뜨리면 임계 구역이 보호되지 않거나 대기자가 깨어나지 않는다. 이런 오류는 특정 실행 순서에서만 드러나므로 보통의 테스트를 통과하기 쉽다. 모니터 같은 상위 수준 구문을 사용하면 위험을 줄일 수 있다.

    </details>

11. **모니터와 조건 변수:** 모니터란 무엇이며, 세마포어와 어떻게 다른가? 조건 변수가 추가로 필요한 이유는 무엇인가?

    <details>
    <summary>정답</summary>

    모니터는 자기 연산들에 대해 **상호 배제를 자동으로 강제하는 ADT**이다. 한 번에 한 스레드만 안에 있을 수 있고, 락과 언락은 프로그래머가 아니라 런타임이 삽입한다. 상호 배제만으로는 버퍼가 비어 있지 않게 될 때까지 기다리는 것 같은 동작을 표현할 수 없으므로 **조건 변수**(`x.wait()`, `x.signal()`)가 필요하다. `wait`는 모니터를 놓아 다른 스레드가 상태를 바꿀 수 있게 하고, `signal`은 상태가 바뀌었을 때 대기자를 깨운다.

    </details>

12. **signal 정책:** 모니터의 **signal-and-wait** 정책과 **signal-and-continue** 정책을 구분하라. 이 정책들은 어떤 문제를 해결하는가?

    <details>
    <summary>정답</summary>

    모니터 안의 스레드 P가 `x.signal()`을 호출하고 다른 스레드 Q가 `x`에서 대기 중이면, 두 스레드 모두 모니터 안의 활성 스레드가 되려 하지만 하나만 가능하다. **Signal-and-wait**에서는 P가 멈추고 Q가 즉시 실행된다. **Signal-and-continue**에서는 P가 모니터를 떠날 때까지 계속 실행되고 그다음에 Q가 실행된다. 언어마다 정책이 다르다. Signal-and-continue에서는 Q가 실행될 때 다른 스레드가 조건을 다시 바꾸었을 수 있으므로 조건 술어를 `while` 루프 안에서 다시 검사해야 한다.

    </details>

13. **데드락:** **데드락**을 정의하고 두 세마포어를 사용한 예시를 들라.

    <details>
    <summary>정답</summary>

    **데드락**은 어떤 프로세스 집합의 모든 프로세스가 그 집합 안의 다른 프로세스만 일으킬 수 있는 사건을 기다리는 상태이다. 세마포어 S, Q(둘 다 1)로 예를 들면, P0은 `wait(S); wait(Q);`를, P1은 `wait(Q); wait(S);`를 실행한다. P0이 S를 획득하고 선점된 뒤 P1이 Q를 획득하고 `wait(S)`를 시도하고, P0이 `wait(Q)`를 시도하면 각자가 상대에게 필요한 것을 들고 있게 된다.

    </details>

14. **우선순위 역전:** 세 우선순위 L < M < H로 우선순위 역전을 설명하라. 우선순위 상속 프로토콜은 이 문제를 어떻게 해결하며, 어떤 실제 사건이 이 문제를 널리 알렸는가?

    <details>
    <summary>정답</summary>

    L이 락을 들고 있을 때 H가 그 락을 요청해 블록되고, M이 실행 가능해져 L을 선점하면(M > L) H가 M 때문에 지연된다. **우선순위 상속**은 L이 H에게 필요한 락을 들고 있는 동안 L의 우선순위를 H 수준으로 일시적으로 올려 M이 L을 선점하지 못하게 한다. L은 임계 구역을 끝내고 락을 푼 뒤 원래 우선순위로 돌아간다. **Mars Pathfinder(1997)** 에서는 반복된 시스템 리셋의 원인이 VxWorks에서 일어난 우선순위 역전으로 밝혀졌고, JPL이 우선순위 상속을 활성화하여 원격으로 해결했다.

    </details>

15. **유한 버퍼:** 세마포어 세 개로 유한 버퍼 문제를 풀어라. `wait` 호출 순서가 중요한 이유는 무엇인가?

    <details>
    <summary>정답</summary>

    `mutex = 1`(이진), `empty = n`, `full = 0`(계수형)을 사용한다. 생산자는 `wait(empty); wait(mutex); insert; signal(mutex); signal(full)`, 소비자는 `wait(full); wait(mutex); remove; signal(mutex); signal(empty)`를 실행한다. **순서가 중요한 이유**: 생산자가 `wait(mutex); wait(empty)`로 순서를 뒤집으면 버퍼가 가득 찼을 때 생산자는 `mutex`를 *든 채* `empty`에서 블록되고, 소비자는 슬롯을 비우러 들어올 수 없어 **데드락**이 된다.

    </details>

16. **Readers-Writers 변형:** 첫 번째와 두 번째 Readers-Writers 문제를 구분하라. 기아를 없앨 수 있는가?

    <details>
    <summary>정답</summary>

    **첫 번째** 문제는 읽기자 우선이다. 쓰기자가 대기 중이어도 읽기자가 들어갈 수 있으므로 **쓰기자 기아**가 생길 수 있다. **두 번째** 문제는 쓰기자 우선이다. 쓰기자가 대기 중이면 새 읽기자가 들어갈 수 없으므로 **읽기자 기아**가 생길 수 있다. 두 변형 모두 우선순위가 낮은 쪽의 기아를 허용하며, 기아를 없애려면 읽기자와 쓰기자를 번갈아 들여보내는 큐 같은 추가 공정성 메커니즘이 필요하다.

    </details>

17. **식사하는 철학자들의 데드락:** 단순한 세마포어 해법이 데드락에 빠지는 이유를 설명하고, 세 가지 해결책을 나열하라.

    <details>
    <summary>정답</summary>

    모든 철학자가 동시에 `wait(chopstick[i])`(왼쪽)를 실행하면 다섯 젓가락이 모두 0이 되고, 각자 오른쪽 젓가락에서 블록되어 **순환 대기로 데드락**이 생긴다. 해결책은 **(1) 동시에 4명**만 식탁에 앉게 하기(사이클 제한), **(2) 양쪽 젓가락을 임계 구역에서 원자적으로 집기**(예: 모니터 해법), **(3) 비대칭 프로토콜**(홀수 번 철학자는 왼쪽 먼저, 짝수 번 철학자는 오른쪽 먼저)로 순환 대기 깨기이다.

    </details>

18. **Windows 동기화 객체:** Windows의 Dispatcher Objects와 Critical-Section Objects를 비교하라. 각각은 언제 사용되는가?

    <details>
    <summary>정답</summary>

    **Dispatcher Objects**(Mutex, Semaphore, Event, Timer)는 signaled/nonsignaled 상태를 갖는 커널 객체이며, nonsignaled 객체를 획득하려는 스레드는 커널에서 블록된다. **Critical-Section Objects**는 **먼저 사용자 공간에서 스핀락을 시도** 하고, 경합이 심해 스핀이 길어질 때만 커널 뮤텍스로 넘어가는 사용자 모드 뮤텍스이다. 흔한 무경합 경우에는 커널을 거치지 않으므로 훨씬 빠르다.

    </details>

19. **Linux의 락:** Linux의 `spinlock_t`와 `mutex`를 비교하라. 두 락이 **비재귀(nonrecursive)** 라는 것은 무엇을 뜻하는가?

    <details>
    <summary>정답</summary>

    `spinlock_t`는 바쁜 대기를 하며 매우 짧은 커널 임계 구역에 적합하고, `mutex`는 더 긴 대기를 위한 **sleeping** 락이다. **비재귀**란 이미 락을 잡은 스레드가 같은 락을 다시 획득하려 하면 데드락이 된다는 뜻이다. 락에는 소유 스레드가 이미 그 락을 들고 있는지 기록하는 내부 카운터가 없다. 재귀적인 획득이 필요해 보이면 같은 락을 다시 잡지 않도록 코드를 구조화해야 한다.

    </details>

20. **POSIX 조건 변수 규칙:** POSIX 조건 변수를 사용할 때 따라야 할 세 가지 규칙을 말하라.

    <details>
    <summary>정답</summary>

    1. `pthread_cond_wait()`는 원자적으로 뮤텍스를 해제하고 블록하며, 깨어날 때 뮤텍스를 다시 획득한다.
    2. `pthread_cond_signal()`은 뮤텍스를 해제하지 않으므로 신호를 보낸 스레드가 직접 `pthread_mutex_unlock()`을 호출해야 한다.
    3. 술어 검사는 `if`가 아니라 항상 **`while`** 루프 안에서 한다. 표준은 spurious wakeup을 허용하며, 깨어난 뒤 뮤텍스를 다시 잡는 사이 다른 스레드가 상태를 바꾸었을 수 있다.

    </details>

21. **Java의 이름 있는 조건:** `ReentrantLock.newCondition()`으로 만든 Java의 이름 있는 `Condition` 객체가 단일 익명 `notify()`보다 유한 버퍼 패턴에 도움이 되는 이유는 무엇인가?

    <details>
    <summary>정답</summary>

    유한 버퍼에는 생산자가 기다리는 버퍼가 가득 차지 않았다는 조건과 소비자가 기다리는 버퍼가 비어 있지 않다는 조건이 따로 있다. 단일 익명 `notify()`로는 실제로는 소비자의 조건이 만족되었는데 런타임이 생산자를 깨울 수 있고(또는 그 반대), 깨어난 스레드는 `while` 조건을 검사한 뒤 다시 잠들어 깨움이 헛되게 된다. **이름 있는 조건**을 쓰면 신호를 보내는 스레드가 만족된 **특정** 조건을 정확히 겨냥할 수 있어 헛된 왕복이 사라진다.

    </details>
