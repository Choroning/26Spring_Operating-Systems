## 1. 배경과 기본 하드웨어

### 1.1 메모리 관리가 필요한 이유

CPU 사용률을 높이려면 OS는 **여러 프로세스를 동시에 메모리에 적재**해야 한다. 둘 이상의 프로세스가 물리 메모리를 공유하는 순간 세 가지 문제가 생긴다.

- **상호 보호:** 한 프로세스가 다른 프로세스의 메모리를 읽거나 덮어쓸 수 없어야 한다.
- **주소 변환:** 모든 프로세스는 0부터 시작하는 깨끗한 주소 공간을 기대하지만, 실제로 모두가 물리 주소 0에 놓일 수는 없다.
- **효율적 공유:** 코드(라이브러리, 커널)는 공유해야 하지만 개인 데이터는 공유되면 안 된다.

> **참고:** **이 토대가 중요한 이유.** 이후의 모든 메모리 주제(페이징, 가상 메모리, 페이지 교체, copy-on-write)는 이 세 가지 성질을 대규모로 강제하기 위한 서로 다른 방법이다.

### 1.2 CPU가 직접 접근할 수 있는 저장소

CPU가 직접 접근할 수 있는 저장소는 레지스터와 주 메모리 두 종류이다.

```text
   +-----------+
   | Register  |   <- ~1 cycle
   +-----------+
   |   Cache   |   <- 몇 cycle (ISA에 투명)
   +-----------+
   |   Main    |   <- 수십~수백 cycle
   |  Memory   |
   +-----------+
   |   Disk    |   <- 수백만 cycle, 직접 접근 불가
   +-----------+
```

*그림 1. 저장 장치 계층과 접근 지연*

> **[컴퓨터구조]** 위 도식은 표준 **메모리 계층 구조(memory hierarchy)** 이며, 각 계층은 용량과 지연 시간을 맞바꾼다. 캐시가 **ISA에 투명(transparent)** 하다는 것은 캐시가 전적으로 하드웨어에 의해 관리된다는 뜻이다. OS도 실행 중인 프로그램도 캐시에 명시적인 load나 store를 발행하지 않으며, CPU가 필요할 때 자동으로 캐시 라인을 채우고 자체 정책으로 내보낸다. 명령어 집합의 load와 store에 노출되는 것은 **레지스터 파일**과 **주 메모리**뿐이므로, OS 교재는 캐시가 없는 것처럼 직접 접근할 수 있는 저장소를 이야기한다.

디스크의 모든 데이터는 CPU가 다루기 전에 **메모리로 적재**되어야 한다. 메모리가 희소하고 경쟁이 심한 자원인 이유가 바로 이것이다.

### 1.3 Base / Limit 레지스터

가장 단순한 하드웨어 보호 방식은 프로세스마다 **base**와 **limit** 레지스터 값을 두는 것이다.

- **Base 레지스터:** 프로세스가 합법적으로 접근할 수 있는 가장 작은 물리 주소이다.
- **Limit 레지스터:** 합법 범위의 *크기*이다(상한 주소가 아니다).
- CPU가 발생시킨 주소는 `base ≤ addr < base + limit`을 만족해야 한다. 위반하면 **OS로 트랩**이 발생한다(사용자 프로그램에서는 segmentation fault로 나타난다).

구체적인 예로, Base = 300040, Limit = 120900이면 접근할 수 있는 범위는 `300040 ~ 420939`이다.

## 2. 주소 바인딩과 MMU

### 2.1 세 가지 바인딩 시점

프로그램의 메모리 주소는 처음부터 저절로 정해져 있지 않고, 어느 시점에 물리 위치에 *바인딩(binding)* 된다. 바인딩 시점이 런타임에 OS가 해야 할 일을 결정한다.

| 바인딩 시점 | 설명 | 특성 |
|------------|------|------|
| **컴파일 시점** | 메모리 시작 주소가 컴파일 시 고정 | **절대 코드(absolute code)** 생성, 시작 주소가 바뀌면 재컴파일 필요 (MS-DOS .COM) |
| **적재 시점** | 로더가 프로그램을 메모리에 배치할 때 시작 주소 고정 | **재배치 가능(relocatable) 코드** 생성, 실행 후 이동 불가 |
| **실행 시점** | 프로그램 실행 *중* 바인딩 | **MMU** 필요, 거의 모든 현대 OS가 사용 |

*표 1. 세 가지 주소 바인딩 시점의 비교*

### 2.2 사용자 프로그램의 다단계 처리

소스 코드는 여러 단계를 거치며, 단계마다 바인딩의 일부를 수행한다.

```text
  source.c   --(compile)-->  object module   (재배치 가능, 심볼명 보유)
             --(link)----->  load module
             --(load)----->  in-memory binary
             --(run)------>  physical reference (MMU)
```

*그림 4. 소스 코드가 컴파일, 링크, 적재, 실행을 거쳐 물리 참조가 되는 과정*

![그림 5. 사용자 프로그램의 다단계 처리](../../images/Week11_p05.png)

*그림 5. 사용자 프로그램의 다단계 처리*

- 주소는 **심볼릭** 주소(변수명)에서 **재배치 가능** 주소(모듈 시작 기준 오프셋)를 거쳐 **절대** 주소(물리 주소)로 바뀐다.

### 2.3 논리 주소 vs 물리 주소

런타임에는 두 주소 공간이 공존한다.

- **논리 주소**(= *가상 주소*)
  - CPU가 명령어를 실행하면서 생성하는 주소이다.
  - 프로세스는 0부터 어떤 최대치까지의 독립적인 공간을 본다.
- **물리 주소**
  - DRAM에 실제로 전달되는 주소이다(Memory Address Register에 적재된다).
  - 실제 공유 범위 `R + 0 … R + max`에 존재한다.

**컴파일 시점**이나 **적재 시점** 바인딩에서는 논리 주소와 물리 주소가 같다. **실행 시점** 바인딩에서는 둘이 다르며 **모든 메모리 참조마다 변환이 필요**하다.

### 2.4 MMU: 메모리 관리 장치

**MMU**는 논리 주소를 물리 주소로 변환하는 하드웨어이다. 가장 단순한 동적 재배치(dynamic relocation) 방식에서는 모든 논리 주소에 **재배치 레지스터(relocation register)** 값을 더하기만 한다.

> **참고:** 이 가장 단순한 설계에서 재배치 레지스터는 1.3절에서 소개한 **base 레지스터**와 같은 물리 레지스터이며, 두 이름은 서로 다른 역할을 강조할 뿐이다. base라는 이름은 limit 검사의 하한을, relocation이라는 이름은 사용자가 보는 0…max를 실제 물리 범위로 옮기는 가산값을 뜻한다.

```text
  logical addr  -->  +-----+
                     | MMU |  + relocation_register  -->  physical addr  -->  DRAM
                     +-----+
```

*그림 6. MMU가 논리 주소에 재배치 레지스터 값을 더해 물리 주소를 만드는 과정*

![그림 7. 재배치 레지스터를 이용한 동적 재배치](../../images/Week11_p07.png)

*그림 7. 재배치 레지스터를 이용한 동적 재배치*

사용자 프로그램은 *오직* 논리 주소 0…max만 본다. MMU가 CPU와 버스 사이의 경로에 있기 때문에 물리 주소를 위조할 방법이 없다.

실제 시스템은 훨씬 정교한 MMU(페이징, 세그멘테이션)를 쓰지만 원리는 같다. 프로그램이 쓰는 주소와 DRAM에 도달하는 주소 사이에 하드웨어가 강제하는 간접층(indirection)이 있다.

### 2.5 동적 적재 (Dynamic Loading)

**동적 적재**는 루틴을 **호출될 때만** 메모리에 적재하는 방식이다. 메인 프로그램은 메모리에 있고, 드물게 쓰이는 루틴(예: 잘 일어나지 않는 오류의 처리기)은 필요할 때까지 디스크에 머무른다.

```text
  메인 프로그램 (메모리)
   ├── routine_A()        이미 적재
   ├── routine_B()        호출 시 적재
   └── error_handler()    에러 발생 시에만 적재  (디스크)
```

*그림 8. 동적 적재에서 루틴별 적재 시점*

동적 적재는 흥미롭게도 **OS 지원 없이** 프로그래머가 구현할 수 있다(프로그래머가 조건부 적재를 직접 배치한다). 전체 프로그램은 크지만 *상주* 크기는 작게 유지된다.

### 2.6 동적 연결과 공유 라이브러리

**정적 연결(static linking)** 은 링크 시점에 라이브러리 코드를 실행 파일에 복사하므로 모든 프로그램이 `libc`의 완전한 사본을 들고 다닌다. **동적 연결(dynamic linking)** 은 바인딩을 *실행 시점*까지 미루고 메모리에 있는 한 사본을 모든 프로세스가 공유한다.

| 측면 | DLL / 공유 라이브러리 이점 |
|------|--------------------------|
| 메모리 절약 | 물리 사본 하나가 모든 프로세스에 서비스 |
| 디스크 절약 | 모든 실행 파일에 라이브러리 코드 중복 없음 |
| 쉬운 업데이트 | 라이브러리 파일만 교체, 사용자 측 재빌드 불필요 |
| 버전 관리 | 여러 버전 공존, 프로그램은 호환되는 것을 선택 |

*표 2. DLL과 공유 라이브러리의 이점*

각 프로그램의 작은 **stub**이 첫 호출 때 라이브러리 루틴을 찾고, 이후에는 호출 지점이 루틴으로 바로 점프하도록 패치한다. 동적 연결은 라이브러리를 프로세스의 보호된 주소 공간에 매핑해야 하므로 OS 지원이 필요하다.

> **[시스템프로그래밍]** **링커(linker)** 는 여러 오브젝트 모듈의 심볼 참조를 주소로 해석해 하나의 실행 파일로 묶고, **로더(loader)** 는 그 실행 파일을 메모리에 올려 실행을 준비한다. 정적 연결에서는 이 심볼 해석이 링크 시점에 끝나지만, 동적 연결에서는 라이브러리 함수에 대한 해석이 실행 시점으로 미뤄진다. 위의 stub이 이 미뤄진 해석을 맡는 코드이며, ELF 형식의 실행 파일에서는 PLT(Procedure Linkage Table)와 GOT(Global Offset Table)가 첫 호출 때 동적 링커가 찾은 함수 주소를 기록해 두고 이후 호출을 그 주소로 바로 보낸다.

```text
  Static Linking                    Dynamic Linking
  +-----------------+               +-----------------+
  | Program A       |               | Program A       |
  | +-------------+ |               | (stub -> libc)  |
  | | libc copy 1 | |               +-----------------+
  | +-------------+ |                        |
  +-----------------+               +-----------------+
  | Program B       |               | Program B       |
  | +-------------+ |               | (stub -> libc)  |
  | | libc copy 2 | |               +-----------------+
  | +-------------+ |                        |
  +-----------------+               +-----------------+
                                    | libc (1 copy)   | <- 공유
                                    +-----------------+

  libc 2MB × 40 프로세스           libc 2MB × 1 사본
  = 80MB 메모리                    = 2MB 메모리
```

*그림 9. 정적 연결과 동적 연결의 libc 사본 수와 메모리 사용량*

### 2.7 세그멘테이션 (Segmentation)

지금까지 MMU는 메모리를 하나의 선형 범위로 제시했다. **세그멘테이션(segmentation)** 은 *프로그래머*가 생각하는 방식 그대로 주소 공간을 노출하는 대안적인(그리고 역사적으로 더 오래된) MMU 방식이다. 주소 공간은 코드용, 전역 데이터용, 스택용, 공유 라이브러리마다 하나씩처럼 가변 크기 **세그먼트(segment)** 의 모음이다.

- **논리 주소**는 단일 숫자가 아니라 **(세그먼트 번호 `s`, 오프셋 `d`)** 쌍이다.
- **세그먼트 테이블**은 세그먼트마다 **base**(시작 물리 주소)와 **limit**(길이)를 보관한다.
- 변환은 `s`로 세그먼트 테이블을 인덱싱하고, `d < limit`을 검사한 뒤(위반 시 트랩) 물리 주소 `base + d`를 만든다.

```text
논리 주소: (s, d)

   세그먼트 테이블
   s | base    | limit
   --+---------+-------
   0 | 1400    | 1000     코드
   1 |  500    |  400     데이터
   2 | 4300    | 1100     스택

  변환 (2, 53):  53 < 1100 OK  ->  4300 + 53 = 4353
```

*그림 10. 세그먼트 테이블과 논리 주소 (2, 53)의 변환*

이는 프로세스 전체에 base와 limit을 하나만 두는 대신 **세그먼트마다 base와 limit을** 두는 방식이다. 따라서 각 논리 단위에 고유한 보호를 부여하고, 세그먼트를 독립적으로 키우거나 세그먼트 단위로 공유할 수 있다. 약점은 가변 분할 연속 할당과 같다. 세그먼트가 **임의의 크기**를 가지므로 그 사이의 빈 물리 메모리가 크기가 제각각인 틈으로 쪼개진다. 즉 세그멘테이션은 **외부 단편화**를 겪는다. 그래서 IA-32(9.1절)는 세그멘테이션을 페이징과 *결합*한다. 세그멘테이션이 `(s, d)`를 선형 주소로 매핑하고, 이어서 페이징이 그 선형 주소를 물리 프레임으로 매핑하여 외부 단편화를 없앤다.

## 3. 연속 메모리 할당

### 3.1 개요와 메모리 보호

역사적으로 가장 단순한 방식은 각 프로세스에 **연속된 물리 메모리 블록 하나**를 주는 것이다.

- 메모리는 **OS 영역**과 **사용자 영역**으로 나뉜다. OS 영역의 위치는 인터럽트 벡터의 위치 같은 요인에 따라 정해지며, Linux와 Windows를 비롯한 많은 OS는 높은 주소에 둔다.
- **홀(hole)** 은 빈 블록이다. 다양한 크기의 홀이 사용자 영역에 흩어져 있다.
- 프로세스가 도착하면 OS는 충분한 크기의 홀을 고른다.

보호는 **재배치 레지스터와 limit 레지스터**로 강제한다. 모든 논리 주소를 먼저 limit 레지스터와 비교해 범위 안에 있는지 검사하고, 통과하면 재배치 레지스터 값을 더해 물리 주소를 만든다. OS 디스패처는 문맥 교환 때 두 레지스터 값을 적재한다.

![그림 11. 재배치 레지스터와 limit 레지스터에 대한 하드웨어 지원](../../images/Week11_p09.png)

*그림 11. 재배치 레지스터와 limit 레지스터에 대한 하드웨어 지원*

### 3.2 가변 분할 방식

프로세스마다 필요에 맞는 **가변 크기 분할**을 준다. 프로세스가 종료되면 홀이 생기고, **인접한 홀은 합쳐져(coalesce)** 더 큰 빈 블록이 된다.

![그림 12. 가변 분할](../../images/Week11_p10.png)

*그림 12. 가변 분할*

문제는 현재 홀 목록이 주어졌을 때 크기 n의 새 요청을 **어느 홀에** 할당할 것인가이다. 이를 **동적 저장소 할당 문제(Dynamic Storage-Allocation Problem)** 라고 한다.

### 3.3 First-fit / Best-fit / Worst-fit

| 전략 | 방법 | 특성 |
|------|------|------|
| **First-fit** | 충분한 크기의 첫 홀에 할당 | 빠름(첫 일치에서 중단), 일반적으로 좋은 사용률 |
| **Best-fit** | 충분한 크기 중 가장 작은 홀에 할당 | 잔여 최소, 전체 스캔 필요, 작은 홀이 많이 생성됨 |
| **Worst-fit** | 가장 큰 홀에 할당 | 가장 큰 잔여 홀을 남김, 직관과 달리 *최악*인 경우가 많음 |

*표 3. 세 가지 할당 전략의 비교*

**경험적 결과:** 시뮬레이션에서 First-fit과 Best-fit은 Worst-fit보다 낫고, First-fit은 비슷한 사용률에서 Best-fit보다 빠르다.

### 3.4 할당 예제

홀(순서대로): 300KB, 600KB, 350KB, 200KB, 750KB, 125KB.
요청 순서: P1 = 115KB, P2 = 500KB, P3 = 358KB, P4 = 200KB, P5 = 375KB.

각 줄은 선택된 홀과 그 홀이 남기는 잔여(괄호 안)를 보여 준다.

```text
First-fit (충분히 큰 첫 홀 사용):
  P1(115) -> 300  홀      (185 남음)
  P2(500) -> 600  홀      (100 남음)
  P3(358) -> 750  홀      (392 남음)
  P4(200) -> 350  홀      (150 남음)
  P5(375) -> 392  잔여 홀  (17 남음)
  => 5개 요청 모두 성공.

Best-fit (들어맞는 가장 작은 홀 사용):
  P1(115) -> 125  홀      (10 남음)
  P2(500) -> 600  홀      (100 남음)
  P3(358) -> 750  홀      (392 남음)
  P4(200) -> 200  홀      (0 남음, 정확히 일치)
  P5(375) -> 392  잔여 홀  (17 남음)
  => 5개 요청 모두 성공.

Worst-fit (가장 큰 홀 사용):
  P1(115) -> 750  홀      (635 남음)
  P2(500) -> 635  잔여 홀  (135 남음)
  P3(358) -> 600  홀      (242 남음)
  P4(200) -> 350  홀      (150 남음)
  P5(375) -> 실패
            (남은 홀: 300, 242, 150, 200, 135, 125, 최대 300 < 375)
```

요점은 정확한 수치가 아니라 **할당 전략에 따라 어떤 요청이 성공하는지가 의미 있게 달라진다**는 것이다. Worst-fit은 항상 *가장 큰* 홀을 깎아 쓰므로 **큰 홀을 일찍 잘게 부순다.** 750KB 홀과 600KB 홀을 작거나 중간 크기인 요청에 써 버린 뒤에는 마지막 375KB 요청을 담을 만큼 큰 홀이 남지 않아, 총 가용 메모리는 충분한데도 **P5가 실패한다**(외부 단편화). First-fit과 Best-fit은 충분히 큰 홀을 남겨 다섯 요청을 모두 완료한다.

### 3.5 외부 단편화 vs 내부 단편화

서로 다른 두 형태의 낭비가 있다.

- **외부 단편화:** 총 여유 메모리는 충분하지만 요청을 담을 만큼 큰 **단일 홀이 없는** 상태이며, 연속성의 문제이다.
- **내부 단편화:** 시스템이 고정 *단위*로 할당할 때 요청이 단위보다 작으면, 할당 영역 *내부*에 남는 공간이 낭비된다.

```text
외부 단편화                         내부 단편화
+--------+                         +---------+
|  P1    |                         |Allocated|  <- 요청: 3.5KB
+--------+                         | (3.5KB) |
|  hole  | 50KB                    |---------|
+--------+                         |  낭비   |  <- 0.5KB
|  P2    |                         | (0.5KB) |
+--------+                         +---------+  <- 할당 단위: 4KB
|  hole  | 30KB
+--------+
|  P3    |  요청: 70KB  총 free: 80KB  최대 연속: 50KB → 실패
```

*그림 13. 외부 단편화와 내부 단편화*

> **참고:** **50% 규칙(Knuth).** first-fit의 통계적 분석에 따르면 N개의 블록이 할당되어 있을 때 약 0.5N개의 블록이 단편화로 추가 손실된다. 즉 전체 1.5N개 블록 중 0.5N개를 쓸 수 없으므로, 장기간 가동되는 가변 분할 시스템에서는 메모리의 약 3분의 1이 외부 단편화로 사용 불가능해질 수 있다. 이 문제가 페이징 도입의 동기가 되었다.

### 3.6 압축 (Compaction)

외부 단편화의 무차별적인 해결책은 **점유된 메모리를 한쪽 끝으로 옮기고** 모든 빈 공간을 반대쪽 끝에 모아 하나의 큰 홀을 만드는 것이다.

```text
Before                  After
+--------+              +--------+
|  P1    |              |  P1    |
+--------+              +--------+
|  hole  |              |  P2    |
+--------+              +--------+
|  P2    |  -- 이동 -> |  P3    |
+--------+              +--------+
|  hole  |              |        |
+--------+              |  hole  |  <- 하나의 큰 연속 블록
|  P3    |              |        |
+--------+              +--------+
```

*그림 14. 압축 전후의 메모리 배치*

압축은 **실행 시점 바인딩**에서만 가능하다(프로세스의 base 레지스터를 실행 중에 바꿀 수 있어야 한다). 또한 비용이 매우 크다. 모든 프로세스를 복사하고 base 레지스터를 갱신하는 동안 시스템이 멈춘다.

더 나은 답은 **페이징**으로 밝혀졌다. 비연속 할당을 하여 애초에 외부 단편화가 생기지 않게 한다.

## 4. 페이징: 기본 방법

### 4.1 페이징 개요

**페이징**은 논리 메모리와 물리 메모리를 분리한다.

- 물리 메모리는 고정 크기 **프레임(frame)** 으로 나눈다.
- 논리 메모리는 같은 크기의 **페이지(page)** 로 나눈다.
- **페이지 테이블**이 프로세스별로 페이지 번호를 프레임 번호에 매핑한다.

결과는 다음과 같다.

- **외부 단편화가 없어진다.** 어떤 빈 프레임이든 어떤 페이지든 담을 수 있기 때문이다.
- **내부 단편화는 남는다.** 각 프로세스의 마지막 페이지는 거의 다 채워지지 않으며, 평균적으로 프로세스마다 반 페이지가 낭비된다.

![그림 15. 논리 메모리와 물리 메모리의 페이징 모델](../../images/Week11_p14.png)

*그림 15. 논리 메모리와 물리 메모리의 페이징 모델*

### 4.2 주소 변환 원리

페이지 크기가 $2^n$바이트, 논리 주소 공간이 $2^m$바이트라 하자(32비트 아키텍처에서는 m = 32, x86-64에서는 m = 48이다. 9.3절 참조). 주소는 다음과 같이 나뉜다.

```text
Logical Address (m bits)
+-------------------+------------------+
| Page number (p)   | Page offset (d)  |
|    (m-n bits)     |    (n bits)      |
+-------------------+------------------+

변환
1. p를 페이지 테이블의 인덱스로 사용.
2. PT[p]에서 프레임 번호 f 읽기.
3. 물리 주소 = (f << n) | d.

Physical Address
+-------------------+------------------+
| Frame number (f)  | Page offset (d)  |
+-------------------+------------------+
```

*그림 16. 논리 주소의 페이지 번호와 오프셋 분할, 물리 주소로의 변환*

**핵심 불변식:** 페이지 오프셋 `d`는 그대로 유지된다. 페이지와 프레임의 크기가 같으므로 그 안의 위치가 같기 때문이다.

> **[컴퓨터구조]** `(f << n) | d`가 `f × page_size + d`와 같은 이유는 다음과 같다. 정수를 왼쪽으로 `n`비트 시프트하면 $2^n$을 곱한 것과 같다. 페이지 크기가 $2^n$이므로 `f << n`은 정확히 `f × page_size`이다. `f << n`의 하위 `n`비트는 모두 0이므로 `n`비트 오프셋 `d`를 OR로 끼워 넣는 것은 `d`를 더하는 것과 같다. 결국 주소를 (페이지 번호, 오프셋)으로 나누는 것은 페이지 크기로 나눈 *몫과 나머지*를 산술 연산 없이 배선만으로 얻는 일이다. 페이지 크기가 항상 2의 거듭제곱인 이유도 여기에 있다. MMU가 나눗셈 회로 없이 배선만으로 오프셋을 떼어 낼 수 있기 때문이다.

### 4.4 내부 단편화와 페이지 크기 트레이드오프

페이지 크기가 2,048바이트이고 프로세스가 72,766바이트를 필요로 한다고 하자.

- 72,766 / 2,048 = 35 페이지 + 1,086바이트이다.
- OS는 **36 프레임**을 할당하므로 내부 단편화는 2,048 − 1,086 = **962바이트**이다.
- 최악의 경우 크기가 *(n × page_size) + 1바이트*인 프로세스는 n+1 프레임이 필요하므로 거의 한 프레임 전체가 낭비된다.

페이지 크기 트레이드오프는 다음과 같다.

| 작은 페이지 | 큰 페이지 |
|-------------|----------|
| 내부 단편화 적음 | 내부 단편화 많음 |
| 페이지 테이블 큼 | 페이지 테이블 작음 |
| I/O 횟수 많음 | 대량 I/O에 효율적 |

*표 4. 페이지 크기에 따른 트레이드오프*

현대 시스템은 보통 **4KB**나 **8KB**를 기본으로 쓰고, 메모리를 많이 쓰는 워크로드를 위해 **2MB**와 **1GB** 거대 페이지(huge page)를 선택적으로 제공한다.

## 5. 페이징 하드웨어 지원: TLB

### 5.1 페이지 테이블을 어디에 둘 것인가

구현 전략은 두 가지이다.

**방법 1: 전용 레지스터.** 페이지 테이블 전체를 특수 하드웨어 레지스터에 저장한다.
- 장점: 조회가 매우 빠르다.
- 단점: 페이지 테이블 항목이 수백 개 정도일 때만 쓸 수 있어 확장성이 없다.

**방법 2: PTBR (Page-Table Base Register).** 페이지 테이블을 주 메모리에 두고, PTBR이 그 시작 주소를 가리킨다.
- 장점: 문맥 교환 때 PTBR만 바꾸면 된다.
- 단점: **모든 메모리 참조에 메모리 접근이 2회 필요하다.** 페이지 테이블 항목(PTE)을 읽는 데 1회, 실제 데이터를 읽는 데 1회이므로 실효 메모리 지연이 두 배가 된다.

### 5.2 TLB: Translation Look-aside Buffer

**TLB**는 최근 변환을 캐시하는 작고 매우 빠른 **연관 메모리(associative memory)** 이다.

> **[컴퓨터구조]** 연관 메모리는 **Content-Addressable Memory (CAM)** 라고도 부른다. 일반 RAM은 *주소*를 받아 그 주소의 *값*을 돌려준다. CAM은 반대로 *값*(여기서는 페이지 번호)을 주면 전용 비교기 하드웨어가 **저장된 모든 키를 한 사이클에 병렬로 비교**해 일치하는 항목의 슬롯 인덱스(와 저장된 데이터)를 돌려준다. 같은 하드웨어 발상이 캐시 태그 배열의 기반이다. 병렬 비교 덕분에 TLB 조회 비용은 거의 없지만 항목당 트랜지스터 비용이 크므로 TLB 크기는 수십에서 수천 항목에 그친다.

- 크기는 보통 32~1,024 항목이다.
- 각 항목은 **(페이지 번호, 프레임 번호)** 와 보호 비트로 이루어진다.
- 조회는 입력 페이지 번호를 **모든 키와 병렬로 비교**하므로 한 사이클에 끝난다.
- TLB 조회는 CPU 파이프라인의 일부로 이루어지므로 TLB 히트에는 관측할 수 있는 추가 지연이 거의 없다.

```text
TLB Hit / Miss 과정:

CPU --p,d--> TLB에서 p 검색
              |
          +---+---+
          |       |
       hit       miss
          |       |
        f 획득  메모리의 페이지 테이블 워크,
          |    (p,f)를 TLB에 삽입
          |       |
          +---+---+
              |
          f + d --> 물리 주소 --> DRAM
```

*그림 20. TLB 히트와 미스 시의 주소 변환 과정*

![그림 21. TLB를 갖춘 페이징 하드웨어](../../images/Week11_p19.png)

*그림 21. TLB를 갖춘 페이징 하드웨어*

TLB가 가득 차면 항목을 내보낸다(LRU, round-robin, random). 일부 항목은 **wired down**되어 내보낼 수 없으며, 보통 OS의 응답성을 유지하기 위해 커널 코드와 데이터가 여기에 해당한다.

### 5.3 ASID: Address-Space Identifier

기본적으로 문맥 교환 때는 **TLB 전체를 플러시**해야 한다. 그렇지 않으면 P1의 TLB 항목이 P2의 주소를 잘못 변환하기 때문이다. 그 비용으로 스케줄러가 프로세스를 바꿀 때마다 TLB 미스가 폭주한다.

> **참고:** **규모 감각.** 1,024 항목 TLB에서 미스 한 번에 약 100 ns가 든다면 플러시 후 TLB를 다시 채우는 데 약 **100 µs**가 걸린다. 이는 Linux의 타임 슬라이스(보통 1밀리초 안팎에서 수 밀리초)에 비해 무시할 수 없는 비율이다. 여기에 문맥 교환 빈도(흔히 초당 수천 회)를 곱하면, 완화하지 않은 TLB 플러시는 상당한 오버헤드가 된다. ASID는 이 간극을 메우려고 설계되었다.

**ASID**는 각 TLB 항목에 프로세스 식별자를 태그한다.

```text
+------+-----+-----+
| ASID |  p  |  f  |
+------+-----+-----+
|  P1  |  3  |  7  |   프로세스 1의 페이지 3 -> 프레임 7
|  P2  |  3  | 12  |   프로세스 2의 페이지 3 -> 프레임 12
+------+-----+-----+
```

*그림 22. ASID로 태그한 TLB 항목*

조회할 때는 페이지 번호와 현재 프로세스의 ASID가 **모두** 일치해야 한다. 여러 프로세스의 항목이 TLB에 공존할 수 있으므로 문맥 교환 비용이 훨씬 줄어든다.

### 5.4 유효 접근 시간 (EAT)

TLB의 성능을 정량화하기 위해 다음과 같이 정의한다.

- α = TLB **히트율**
- M = 주 메모리 접근 시간
- T = TLB 접근 시간

```text
EAT = α · (T + M) + (1 − α) · (T + 2M)
```

> **[확률및통계]** 이 식은 확률의 표준 **기댓값(expected value)** 기법 $E[X] = \sum P(\text{case}) \times \text{cost}(\text{case})$로 유도한다.
> - **히트**(확률 α)이면 T(항상 지불하는 TLB 조회)와 M(실제 데이터에 대한 메모리 접근 1회)을 지불하므로 `T + M`이다.
> - **미스**(확률 1 − α)이면 T(실패한 TLB 조회), M(페이지 테이블 항목을 메모리에서 읽기), M(이어서 실제 데이터 읽기)을 지불하므로 `T + 2M`이다.
> - 각 경우에 확률을 곱해 더한다.

**수치 예** (M = 100 ns, T = 10 ns):

```text
α = 0.80:  EAT = 0.80·110 + 0.20·210 = 88 + 42  = 130 ns  (raw 대비 30% 저하)
α = 0.98:  EAT = 0.98·110 + 0.02·210 = 107.8 + 4.2 = 112 ns  (~ 2% 저하)
α = 0.99:  EAT = 0.99·110 + 0.01·210 = 108.9 + 2.1 = 111 ns  (~ 1% 저하)
```

> **참고:** 위 괄호 안의 저하율은 기준이 서로 다르다. α = 0.80 줄은 raw 메모리 접근 시간 100 ns를 기준으로 한 값이고, 나머지 두 줄은 TLB 히트 시의 접근 시간 T + M = 110 ns를 기준으로 한 값이다. raw 100 ns를 기준으로 하면 α = 0.98은 12%, α = 0.99는 11% 저하이다. TLB 조회가 파이프라인에 통합되어 T를 무시할 수 있으면 EAT는 $\alpha M + (1 - \alpha) \times 2M$이 된다.

교훈은 다음과 같다. 높은 TLB 히트율(98% 이상이며, *공간* 지역성과 *시간* 지역성 덕분에 실제 워크로드에서 쉽게 달성된다)은 TLB 없이 모든 참조가 메모리 접근 2회(200 ns)를 치르는 경우에 비해 페이징의 비용을 거의 없앤다.

## 6. 페이징: 보호와 공유 페이지

### 6.1 보호 비트와 유효/무효 비트

페이지 테이블 항목마다 추가 비트가 있다.

**권한 비트:**
- **R/W:** 읽기 전용인지 읽기/쓰기인지를 나타낸다.
- **X:** 실행 가능 여부를 나타낸다.
- 보호를 위반하는 참조는 하드웨어 트랩을 일으키며, OS는 보통 해당 프로세스에 `SIGSEGV`를 전달한다.

**유효/무효 비트:**
- *유효(Valid)*: 페이지가 프로세스의 논리 주소 공간에 속한다.
- *무효(Invalid)*: 이 프로세스가 사용하지 않는 페이지이며, 참조하면 트랩이 발생한다.

이 비트는 프로세스가 실제로 쓰는 주소 공간이 이론적 최대보다 훨씬 작은 일반적인 상황을 처리한다. 페이지 테이블을 실제로 쓰는 부분으로 줄이기 위해 하드웨어는 테이블의 실제 길이를 제한하는 **PTLR (Page-Table Length Register)** 을 제공한다.

## 7. 페이지 테이블 구조

### 7.1 단일 페이지 테이블의 확장성 문제

가상 페이지마다 항목이 하나씩 있는 평탄한 페이지 테이블은 작은 주소 공간에서는 괜찮지만 빠르게 커진다.

```text
32-bit 주소, 4 KB (= 2^12) 페이지:
  항목 = 2^32 / 2^12 = 2^20 ≈ 1,048,576
  항목당 4 bytes → 페이지 테이블 = 프로세스당 4 MB

64-bit 주소, 4 KB 페이지:
  항목 = 2^64 / 2^12 = 2^52 ≈ 4·10^15
  항목당 8 bytes → 페이지 테이블 ≈ 32 PB (!)
```

한 프로세스의 페이지 테이블을 위해 연속된 물리 메모리 4 MB를 찾기도 어렵고, 32 PB는 말할 것도 없다. 고전적인 해결책은 세 가지이다.

1. **계층적 페이징(hierarchical paging)** (다단계)
2. **해시 페이지 테이블(hashed page tables)**
3. **역 페이지 테이블(inverted page tables)**

### 7.2 계층적 페이징

페이지 테이블 자체를 페이징한다.

```text
Logical address (32-bit, 4KB 페이지, 2단계):
+----------+----------+----------+
|   p1     |   p2     |    d     |
| 10 bits  | 10 bits  |  12 bits |
+----------+----------+----------+

  p1  →  외부 페이지 테이블 (1024 항목)
  p2  →  내부 페이지 테이블 (1024 항목)
  d   →  페이지 오프셋
```

![그림 27. 2단계 32비트 페이징 아키텍처의 주소 변환](../../images/Week11_p25a.png)

*그림 27. 2단계 32비트 페이징 아키텍처의 주소 변환*

이것이 고전적인 **순방향 매핑 페이지 테이블(forward-mapped page table)** 이다. *가상 페이지 번호로 인덱싱*하는 전통적인 페이지 테이블로, 가상 주소에서 출발해 테이블 단계를 앞으로 따라가며 프레임에 도달한다. 이는 프레임 번호로 인덱싱되어 특정 가상 페이지를 찾으려면 검색해야 하는 **역(inverted) 페이지 테이블**(7.5절)과 반대 방향이다. 큰 이점은 사용하지 않는 주소 공간 영역의 내부 페이지 테이블은 **메모리에 할당되지 않는다**는 것이다. 자료구조 관점에서 보면, 외부 테이블은 1024개 포인터의 배열이고 각 포인터는 내부 페이지 테이블(4 KB, 1024 항목)을 가리키거나 **null(무효)** 이다. null인 외부 항목을 따라가면 매핑 없음으로 OS에 트랩되며, 그 항목이 담당하는 가상 주소 공간 4 MB는 페이지 테이블 자체에 물리 메모리를 *전혀* 쓰지 않는다. 보통 프로세스는 4 GB 가상 공간의 작은 부분만 쓰므로 대부분의 외부 항목이 null로 남고, 실제로 쓰는 가지에만 비용을 치른다.

### 7.3 64비트에서 계층적 페이징의 한계

단순한 2단계 페이징을 64비트 주소 공간에 적용하면 다음과 같다.

```text
+----------+----------+----------+
|    p1    |    p2    |    d     |
|  42-bit  |  10-bit  |  12-bit  |
+----------+----------+----------+

외부 테이블 = 2^42 항목 = 2^44 bytes = 16 TB  → 여전히 불가능
```

*그림 28. 64비트 주소에 2단계 페이징을 적용한 주소 구성*

단계를 더 추가하면 도움이 되지만 금방 비현실적이 된다.

```text
3단계 (4KB 페이지): 두 내부 단계를 페이지 크기로 유지
  (각 10비트 = 1024 항목), 외부 단계에는
  52 - 10 - 10 = 32비트가 남음:
    외부 테이블 = 2^32 항목 x 4 B = 2^34 bytes = 16 GB  → 여전히 큼
더 밀어붙이면: 외부 테이블이 감당 가능한 크기로 줄기까지
  약 6~7단계 필요 → 단계마다 메모리 접근 1회씩 드는
  참조당 워크 비용이 급증.
```

따라서 실제 64비트 시스템은 32비트와 같은 단위의 균일한 다단계 페이지 테이블을 쓰지 않는다. **희소한 주소 공간 사용을 활용한 4단계 페이징**(x86-64는 가상 주소를 48비트로 제한한다)이나 아래의 대안을 쓴다.

### 7.4 해시 페이지 테이블

테이블을 **가상 페이지 번호의 해시**로 인덱싱한다.

```text
hash(p) → (p, f, next) 항목 체인
체인 워크하면서 p 일치 찾기
```

![그림 29. 해시 페이지 테이블](../../images/Week11_p25b.png)

*그림 29. 해시 페이지 테이블*

각 버킷은 충돌한 항목을 연결 리스트로 보관한다. 이는 자료구조의 표준 **분리 연쇄(separate chaining)** 충돌 해결 방식이다. 버킷에 저장되는 항목은 `(가상 페이지, 프레임, next)` 형태이고, `next`가 같은 버킷의 다음 충돌 항목을 가리킨다. 페이지 `p`를 변환할 때는 `hash(p)`를 계산하고 그 버킷의 연결 리스트를 따라가다가 저장된 가상 페이지가 `p`와 같은 노드에서 멈춘다. 적재율(load factor)을 낮게 유지하면 평균 조회는 $O(1)$이고 최악은 $O(\text{체인 길이})$이다. 테이블 크기가 이론적 최대가 아니라 실제로 쓰는 페이지 수에 비례하므로 **희소한** 주소 공간(64비트 범위의 대부분이 미사용)에 적합하다.

**클러스터 페이지 테이블(clustered page table)** 은 인접한 여러 페이지의 매핑을 한 항목에 저장해 해시 오버헤드를 분산한다. 64비트의 희소한 주소 공간에 특히 잘 맞는다.

### 7.5 역(Inverted) 페이지 테이블

자료 구조를 뒤집어 **프레임 번호로 인덱싱되는 단일 전역 테이블**을 유지한다(물리 프레임마다 항목 하나).

```text
Inverted PT:
  frame_id | (pid, virtual_page)
  -------- | ---------------------
     0     | (P3, 0x4012)
     1     | (P1, 0x000A)
     ...
```

*그림 30. 프레임 번호로 인덱싱되는 역 페이지 테이블의 항목*

![그림 31. 역(inverted) 페이지 테이블](../../images/Week11_p26.png)

*그림 31. 역(inverted) 페이지 테이블*

- **장점:** 전체 크기가 가상 메모리가 아니라 물리 메모리에 비례하므로 크게 절약된다.
- **단점:** 조회는 *가상* 주소로 하므로 OS가 전체 테이블을 검색해야 한다. 해법은 역 테이블 *위에 얹는* **보조 해시 테이블**이다. `(pid, 가상 페이지)`를 해시해서 **프레임 인덱스**(역 테이블의 행)를 얻는다. 이는 7.4절의 해시 페이지 테이블과 구조적으로 다르다. 그곳에서는 해시가 페이지 테이블을 *대체*하지만, 여기서는 프레임으로 인덱싱되는 별개 구조의 조회를 가속할 뿐이다.
- **한계:** 각 프레임은 정확히 하나의 (pid, 가상 페이지)에 매핑된다. 따라서 같은 프레임이 여러 프로세스의 페이지 테이블에 나타나는 **공유 페이지**를 표현하기 어렵다.

### 7.6 비교

| 구조 | 장점 | 단점 | 적합 |
|------|------|------|------|
| 단일 | 단순, 빠름 | 프로세스당 거대 | 작은 주소 공간 |
| 계층 | 미사용 영역 스킵 | 64비트에서 단계 폭주 | 32비트 시스템, x86-64 (4단계) |
| 해시 | 크고 희소한 VA 처리 | 해시 충돌 오버헤드 | 64비트, 희소 VA |
| 역 | 크기가 물리 메모리에 비례 | 검색 느림, 공유 어려움 | 큰 물리 RAM |

## 8. 스와핑

### 8.1 표준 스와핑

전체 프로세스를 메모리에서 **백킹 스토어**(이 목적으로 디스크에 예약한 영역)로 **swap out**하고, 다시 스케줄될 때 **swap in**한다.

![그림 32. 디스크를 백킹 스토어로 사용하는 두 프로세스의 표준 스와핑](../../images/Week11_p28.png)

*그림 32. 디스크를 백킹 스토어로 사용하는 두 프로세스의 표준 스와핑*

- 시스템이 과부하일 때 다른 프로세스를 위한 메모리를 확보한다.
- **비용이 매우 크다.** 프로세스 전체를 디스크로 옮기는 데 초 단위 시간이 걸려 어떤 타임 슬라이스보다도 훨씬 길다.
- 현대 OS에서는 거의 쓰지 않는다.

### 8.2 페이지 단위 스와핑

현대의 방식은 **페이지 단위**로 동작한다.

- **Page out:** 특정 페이지를 메모리에서 백킹 스토어로 내보낸다.
- **Page in:** 특정 페이지를 요청이 있을 때 백킹 스토어에서 적재한다.
- 프로세스 전체가 아니라 *필요한* 페이지만 옮기므로 더 빠르고, 더 세밀하며, 훨씬 효율적이다.

![그림 33. 페이징을 이용한 스와핑](../../images/Week11_p30.png)

*그림 33. 페이징을 이용한 스와핑*

이것이 **가상 메모리**의 기반이며, 12주차에서 자세히 다룬다.

### 8.3 모바일 시스템의 스와핑

대부분의 모바일 OS는 스와핑을 **지원하지 않는다.** 이유는 다음과 같다.

- **플래시 메모리는 쓰기 수명이 제한**되어 있어 스와핑이 저장 장치를 마모시킨다.
- 플래시와 RAM 사이의 **처리량이 데스크톱 SSD보다 훨씬 낮다.**
- **저장 용량**이 애초에 작다.

대안 전략은 다음과 같다.

- **iOS:** 메모리가 부족하면 앱에 알려 자발적으로 메모리를 반납하게 하고, 협조하지 않는 앱은 종료한다.
- **Android:** 프로세스를 종료하기 전에 앱의 상태를 직렬화해 플래시에 저장한다. 새 프로세스이지만 사용자는 빠른 재시작으로 느낀다.

## 9. 실제 아키텍처

### 9.1 IA-32

32비트 x86이며, **세그멘테이션과 페이징**을 함께 쓴다.

- **논리 주소**는 (세그먼트 셀렉터, 오프셋) 쌍이다.
- 세그멘테이션 하드웨어가 이를 **선형 주소(linear address)** 로 매핑한다.
- 페이징이 선형 주소를 물리 주소로 매핑한다.
- 페이지 크기는 **4 KB**이다(**PSE, Page Size Extension**을 쓰면 **4 MB** 거대 페이지도 쓸 수 있다).

*그림 36. IA-32의 페이징*

### 9.2 IA-32 PAE

**PAE (Page Address Extension)** 는 32비트 프로세서가 4GB를 넘는 물리 RAM에 접근할 수 있게 한다(Intel의 공식 명칭은 Physical Address Extension이다).

- 페이지 테이블 항목을 **32비트에서 64비트로** 확장한다.
- 물리 프레임 번호를 20비트에서 **24비트**로 넓힌다(12비트 오프셋을 더해 36비트 물리 주소, 즉 64GB).
- Linux와 macOS는 PAE를 지원했고, 32비트 일반 사용자용 Windows는 PAE를 켜도 4GB로 제한되었다.

![그림 37. 페이지 주소 확장(PAE)](../../images/Week11_p34a.png)

*그림 37. 페이지 주소 확장(PAE)*

### 9.3 x86-64

원래 AMD64로 나온 뒤 Intel도 채택한 64비트 확장 아키텍처이다.

- **48비트 가상 주소 공간** = 256 TB이다. 쓰지 않는 상위 비트는 비트 47의 부호 확장이어야 하며, 이런 주소를 canonical address라고 한다. 즉 64비트 포인터 중 정보를 담는 것은 하위 48비트뿐이며, 비트 48~63은 모두 비트 47과 같아야 한다(**전부 0이거나 전부 1**). canonical이 아닌 포인터를 역참조하면 #GP 일반 보호 폴트가 발생한다. 소프트웨어가 상위 비트에 다른 정보를 넣어 쓰지 못하게 미리 막아 두면, 미래 CPU가 주소 공간을 넓혀도 기존 소프트웨어가 깨지지 않는다.
- PAE 방식의 확장으로 **52비트 물리 주소** = 4 PB를 지원한다.
- 페이지 크기는 **4 KB**, **2 MB**, **1 GB**이다.
- 4단계 페이지 테이블(PML4 → PDPT → PD → PT)을 쓴다. 최신 칩은 57비트 가상 주소를 위해 5단계를 추가한다.
- 세그멘테이션은 사실상 비활성이다(평탄한 64비트 주소 공간).

![그림 38. x86-64 선형 주소](../../images/Week11_p34b.png)

*그림 38. x86-64 선형 주소*

### 9.4 ARMv8

모바일과 임베디드 분야의 지배적인 64비트 아키텍처이다.

- **2단계 TLB:** 명령어용과 데이터용 micro-TLB가 따로 있고, 그 뒤에 더 큰 main TLB가 있다.
- **ASID**를 하드웨어로 지원하므로 문맥 교환 때 플러시를 피한다.

## 10. 실습: 메모리 할당 시뮬레이터

### 10.1 실습 목표와 자료 구조

**목표:** 메모리 블록 리스트를 관리하는 프로그램을 구현하고, 같은 요청 시퀀스로 First-fit, Best-fit, Worst-fit을 비교한다.

요구 사항은 다음과 같다.
- 메모리를 블록의 연결 리스트(start, size, status, owner)로 표현한다.
- 세 전략으로 각각 할당한다.
- 해제할 때 인접한 빈 블록을 합친다.
- 레이아웃 스냅샷, 할당 성공과 실패, 외부 단편화 크기를 출력한다.

```c
typedef struct Block {
    int start;        // 시작 주소
    int size;         // 블록 크기
    int allocated;    // 0 = free, 1 = allocated
    char process[10]; // 소유 프로세스 이름
    struct Block* next;
} Block;
```

> **[자료구조]** 주소순 단일 연결 리스트는 필요한 연산을 지원한다. 홀 찾기는 순차 접근이므로 $O(n)$이고, 블록 분할은 포인터 수정만으로 $O(1)$이다. 해제할 블록과 그 앞 블록을 찾고 나면 인접 홀 병합도 이웃 확인으로 $O(1)$이다. **First-fit은** 첫 일치 항목에서 탐색을 끝내므로 실제 탐색 비용이 n보다 작을 수 있다. **Best-fit과 Worst-fit은** 충분한 홀 중 가장 작은 홀이나 가장 큰 홀을 찾기 위해 매번 전체 리스트를 스캔하므로 $O(n)$이 걸린다. 이 때문에 First-fit이 보통 더 빠르다. glibc의 ptmalloc 같은 실전 할당자는 크기별로 나눈 bin(free list)을 써서 리스트 전체를 스캔하지 않고 알맞은 크기의 블록을 찾으며, 할당자에 따라 큰 블록에는 트리 구조를 써서 탐색 비용을 $O(\log n)$ 수준으로 낮추기도 한다.

### 10.2 실습 함수와 입출력 예

```c
Block* first_fit(Block* head, int size);   // 충분한 첫 홀
Block* best_fit(Block* head, int size);    // 충분한 가장 작은 홀
Block* worst_fit(Block* head, int size);   // 가장 큰 홀
void   release(Block* head, char* process);// 해제 + 인접 합치기
void   print_memory(Block* head);
```

예시 트레이스는 다음과 같다.

```text
Input
  Memory size: 1024
  Allocate P1: 200
  Allocate P2: 350
  Allocate P3: 150
  Release P2
  Allocate P4: 300

Output (First-fit)
  [  0- 199] P1 (200)
  [200- 549] FREE (350)      <- P2 해제 후
  [550- 699] P3 (150)
  [700-1023] FREE (324)

  Allocate P4(300) → First-fit → [200-499] P4
  [  0- 199] P1 (200)
  [200- 499] P4 (300)
  [500- 549] FREE (50)       <- 잔여 홀
  [550- 699] P3 (150)
  [700-1023] FREE (324)

  외부 단편화 = 50 + 324 = 374 bytes
```

확장 과제로는 무작위 요청 스트림을 공급해 전략별 평균 외부 단편화를 비교하고, 50% 규칙을 실험적으로 검증할 수 있다.

## 점검 문제

1. CPU가 주 메모리는 직접 접근할 수 있지만 디스크는 그렇지 않은 이유는?

   <details>
   <summary>정답</summary>

   CPU의 load와 store 명령어가 다룰 수 있는 것은 레지스터와 주 메모리뿐이며, 주 메모리에는 메모리 버스로 주소를 발행해 접근한다. 아키텍처가 직접 접근할 수 있다고 노출하는 저장 계층이 이 둘이다. 디스크는 별도의 I/O 서브시스템(컨트롤러, DMA, 드라이버) 뒤에 있어서, 도달하려면 OS가 매개하는 명시적 전송(수백만 사이클 규모)이 필요하다. 디스크의 데이터를 실행하거나 읽으려면 OS가 먼저 그 데이터를 메모리에 **적재**해야 한다.

   </details>

2. 논리 주소와 물리 주소를 구분하시오. 어느 바인딩 방식에서 둘이 동일한가?

   <details>
   <summary>정답</summary>

   **논리 주소**는 CPU가 프로그램을 실행하면서 생성하는 주소이며, 프로세스는 자기만의 공간 0…max를 본다. **물리 주소**는 DRAM에 도달하는 주소이다. **컴파일 시점**이나 **적재 시점** 바인딩에서는 둘이 같다(런타임 변환이 없다). **실행 시점** 바인딩에서는 MMU가 모든 참조를 변환하므로 둘이 달라진다.

   </details>

3. MMU의 역할은? Base+Limit MMU가 프로세스를 어떻게 보호하는가?

   <details>
   <summary>정답</summary>

   MMU는 CPU와 메모리 버스 사이에 있으며 **모든 논리 주소를 물리 주소로 변환**한다. 가장 단순한 base+limit 형태에서는 (a) 논리 주소가 **limit**보다 작은지 검사해 그렇지 않으면 트랩을 일으키고, (b) **base** 레지스터 값을 더해 물리 주소를 만든다. base와 limit은 **커널 모드**에서만 바꿀 수 있으므로 사용자 프로세스는 자기 영역을 벗어날 수 없다.

   </details>

4. 정적 연결과 동적 연결을 비교하시오. 공유 라이브러리가 *공유*라 불리는 이유는?

   <details>
   <summary>정답</summary>

   **정적 연결**은 빌드 시점에 라이브러리 코드를 각 실행 파일에 복사하므로 프로세스마다 자기 사본을 가진다. **동적 연결**은 라이브러리 호출을 stub으로 남겨 두고, 실행 시점에 로더가 메모리에 있는 단일 라이브러리 사본을 매핑하고 stub을 패치한다. 라이브러리가 *공유*라고 불리는 이유는 물리 프레임 한 벌이 코드(보통 읽기 전용)를 담고 모든 호출자가 그것을 쓰기 때문이다. 메모리와 디스크를 절약하고, 한 번의 업데이트로 모든 호출자가 고쳐진다.

   </details>

5. 같은 홀 리스트에서 First-fit, Best-fit, Worst-fit을 따라가시오. Worst-fit이 보통 최악인 이유는?

   <details>
   <summary>정답</summary>

   First-fit은 요청을 만족하는 첫 홀을 찾으면 멈춘다. Best-fit은 리스트 전체를 스캔해 충분한 홀 중 가장 작은 것을 고르고, Worst-fit은 가장 큰 홀을 고른다. 3.4절의 예에서는 First-fit과 Best-fit이 다섯 요청을 모두 할당하지만 Worst-fit은 P5(375KB)를 할당하지 못한다. 가장 큰 잔여 홀을 남긴다는 Worst-fit의 직관은 역효과를 낸다. 가장 큰 홀부터 깎아 써서 미래의 큰 요청에 맞는 유일한 홀을 없애기 때문이다. First-fit과 Best-fit은 큰 홀을 보존하며, First-fit은 전체 스캔이 필요 없어 더 빠르다.

   </details>

6. 외부 단편화와 내부 단편화를 구분하시오. 50% 규칙을 진술하시오.

   <details>
   <summary>정답</summary>

   **외부 단편화**는 전체 여유 메모리는 충분하지만 연속된 단일 홀이 부족한 상태이다. **내부 단편화**는 할당 단위가 요청보다 커 할당 영역 안의 공간이 낭비되는 현상이다. Knuth의 first-fit **50% 규칙**에 따르면 N개 블록이 할당될 때 약 0.5N개 블록이 외부 단편화로 추가 손실되어 전체 메모리의 약 3분의 1을 사용할 수 없게 된다. 이 문제는 페이징 도입의 동기가 되었다.

   </details>

7. 페이징 주소 변환을 따라가시오. 오프셋이 변환되지 않고 그대로 통과하는 이유는?

   <details>
   <summary>정답</summary>

   논리 주소를 `(page #, offset)`으로 나눈다. page #로 페이지 테이블을 인덱싱해 **frame #** 를 얻는다. 물리 주소는 `(frame # << offset_bits) | offset`이다. **오프셋은 그대로**인데, 페이지와 프레임의 크기가 같아서 페이지 안의 위치와 그 페이지를 담은 프레임 안의 위치가 같기 때문이다. 상위의 페이지 번호만 변환된다.

   </details>

8. TLB가 해결하는 문제와 그 방법은? ASID가 추가로 무엇을 해결하는가?

   <details>
   <summary>정답</summary>

   TLB가 없으면 모든 메모리 참조에 메모리 접근이 *2회*(PTE 읽기, 데이터 읽기) 필요하다. TLB는 최근 (페이지, 프레임) 변환을 CPU 파이프라인 안의 연관 메모리에 캐시하며, 히트하면 페이지 테이블을 읽는 메모리 접근이 필요 없다. **ASID**는 각 TLB 항목에 소유 프로세스를 태그하므로 문맥 교환 때 TLB를 플러시할 필요가 없고, 여러 프로세스의 변환이 공존할 수 있다. ASID가 없으면 문맥 교환마다 다음 프로세스에서 TLB 미스가 폭주한다.

   </details>

9. M = 100 ns, T = 10 ns, α = 0.99일 때 EAT를 계산하시오. 저하는 어디에서 오는가?

   <details>
   <summary>정답</summary>

   $\text{EAT} = 0.99 \times (10+100) + 0.01 \times (10+200) = 108.9 + 2.1 = 111$ ns이다. raw 메모리(100 ns)에 비해 약 11 ns(11%) 느리며, 그중 10 ns는 모든 참조마다 치르는 TLB 조회 자체이고 약 1 ns는 분산된 미스 비용이다. 99% TLB 히트율이면 TLB가 없을 때(200 ns)에 비해 페이징의 비용이 거의 사라진다는 뜻이다.

   </details>

10. 단일 페이지 테이블이 64비트로 확장되지 않는 이유, 균일 2단계 페이징도 작동하지 않는 이유는?

    <details>
    <summary>정답</summary>

    단일 페이지 테이블은 $2^{64} / 2^{12} = 2^{52} \approx 4.5 \times 10^{15}$개 항목에 항목당 8바이트가 들어 프로세스당 약 32 PB가 되므로 불가능하다. 균일한 2단계에서 `p1`이 42비트, `p2`가 10비트이면 *외부* 테이블만 $2^{42}$개 항목(항목당 4바이트이면 16 TB)이 되어 역시 불가능하다. 3단계나 4단계의 균일한 구성도 중간 테이블이 너무 크다. 실제 64비트 시스템은 **계층적 페이징과 희소 할당**(쓰지 않는 가지를 건너뜀)을 함께 쓰거나 **해시 또는 역** 페이지 테이블 같은 대체 구조를 쓴다.

    </details>

11. 역 페이지 테이블이 잘 맞는 상황은? 주요 한계는?

    <details>
    <summary>정답</summary>

    **물리 메모리가 가상 메모리보다 훨씬 작을 때** 유리하다. 역 테이블의 크기는 프로세스별 가상 공간이 아니라 RAM에 비례하기 때문이다. 주요 한계는 각 물리 프레임에 항목이 *하나*뿐이라는 점이다. 따라서 여러 프로세스의 가상 주소 공간에 같은 프레임이 나타나는 **공유 페이지**를 모델링하기 어려우며, 보조 자료 구조나 체인이 필요하다. 해시가 없으면 검색도 느리지만, 조회용 해시와 TLB를 함께 쓰면 완화된다.

    </details>

12. 모바일 OS가 대부분 스와핑을 구현하지 *않는* 이유는?

    <details>
    <summary>정답</summary>

    세 가지 이유가 있다. (1) 플래시는 쓰기 수명이 제한되어 스왑 페이지 기록이 저장 장치를 마모시킨다. (2) 플래시에서 RAM으로의 처리량은 데스크톱 SSD보다 낮아 스왑 인과 스왑 아웃이 느리다. (3) 휴대전화는 저장 공간도 작다. iOS와 Android는 스왑 대신 앱을 종료해 메모리를 회수한다. iOS는 먼저 앱에 메모리 회수를 요청한 뒤 종료하고, Android는 빠른 재시작을 돕기 위해 앱 상태를 플래시에 저장한다.

    </details>

13. 페이지 크기 트레이드오프는 무엇이며 시스템이 4~8 KB 정도로 수렴한 이유는?

    <details>
    <summary>정답</summary>

    작은 페이지는 내부 단편화가 적지만 페이지 테이블이 크고 (작은) I/O가 많아진다. 큰 페이지는 페이지 테이블이 작고 대량 I/O에 효율적이지만 내부 단편화가 크다. 4~8 KB는 일반적인 데스크톱과 서버 워크로드에서 이 둘의 균형을 잡는 지점이다. 현대 시스템은 TLB 압박이 내부 단편화 낭비보다 중요한 대용량 RAM 워크로드(데이터베이스, VM)를 위해 **2 MB와 1 GB 거대 페이지**를 선택적으로 제공한다.

    </details>

14. 공유 페이지가 작동하는 방식과 읽기 전용 요건이 보호하는 것은?

    <details>
    <summary>정답</summary>

    두 프로세스의 페이지 테이블이 특정 가상 페이지를 *같은* 물리 프레임에 매핑한다(예: libc 텍스트). OS는 두 페이지 테이블의 항목에 모두 **읽기 전용**을 표시한다. 읽기 전용 강제가 공유를 *안전*하게 만든다. 어느 프로세스도 공유 프레임을 수정할 수 없으므로, 한 프로세스가 자기 메모리로 여기는 영역이 다른 프로세스의 쓰기로 바뀌는 일이 생기지 않는다. 재진입 코드는 자기 텍스트에 쓸 필요가 없으므로 이 방식에 자연스럽게 들어맞는다.

    </details>

15. 압축에는 왜 실행 시점 바인딩이 필요하며, 페이징에서는 왜 압축 자체가 필요 없는가?

    <details>
    <summary>정답</summary>

    압축은 프로세스의 바이트를 새 범위로 물리적으로 옮긴다. 프로세스가 계속 실행되려면 *메모리에 있는 동안* base 레지스터가 갱신되어야 하며, 이를 가능하게 하는 것이 바로 실행 시점 바인딩이다. 페이징은 *물리적으로 연속된 할당을 요구하지 않으므로* 이 문제 자체를 피한다. 페이지 테이블의 간접성이 이미 임의의 가상 페이지를 임의의 물리 프레임에 둘 수 있게 하므로 압축할 것이 없다.

    </details>
